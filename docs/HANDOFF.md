# Poco F3 (alioth) → Arch Linux ARM на mainline-ядре

Состояние на 01.09.2026, 15:55 MSK. Аппарат рабочий, загружается, доступен по сети.

---

## 1. Что это

Xiaomi Poco F3, кодовое имя `alioth`, модель `M2012K11AG`, SoC SM8250 (Snapdragon 870).
Запасной аппарат, данные на нём не нужны. Задача — довести Linux до максимума
возможного, из интереса.

Цепочка загрузки: **XBL → ABL → Mu-Silicium UEFI (в разделе `boot`) → systemd-boot → ядро 6.15.1**.

## 2. Как подключиться

```bash
ssh root@10.15.19.82              # по USB, телефон сам раздаёт DHCP
screen /dev/cu.usbmodem101 115200 # последовательная консоль по тому же кабелю
```

Пароль `root` / `root`. Ключ с Mac уже прописан в `authorized_keys`.
Wi-Fi подключён к `Carantine_5G` через NetworkManager, адрес выдаётся по DHCP
и меняется — надёжнее ходить по USB-адресу, он постоянный.

Пользователь графической оболочки — `phone` с паролем `123456` (он же пин-код
на экране блокировки, там цифровая клавиатура). Вход автоматический.

Мелочь, стоившая времени: **`pkill -f <шаблон>` через ssh убивает собственный
сеанс**, если шаблон совпадает с командной строкой. Нужен `pkill -x`.

Меню загрузчика видно на экране, управляется клавишами громкости:

| пункт | что грузит |
|---|---|
| `Arch Linux (no GPU, rescue)` | то же ядро с `initcall_blacklist=msm_drm_register` — графика не поднимается вовсе, экран остаётся с мусором от UEFI, но ssh по USB работает всегда |
| `Arch Linux (current)` | `/efi/Image` — то, что залито последним |
| `Arch Linux (fallback, known good)` | `/efi/Image.ok` — копия заведомо рабочего ядра |

Порядок задан полем `sort-key`, безопасный пункт стоит первым и выбран по умолчанию.
**`default` в `loader.conf` срабатывает не всегда** — надёжнее одноразовый выбор:
`bootctl set-oneshot 01-current.conf`, он же самоочищается после загрузки, так что
следующий заход снова придёт в безопасный пункт.
**Кириллицу шрифт UEFI не рисует** — заголовки только латиницей.

## 5. Решённая проблема: карта памяти (была PAS / TrustZone)

**Симптом.** `adsp`, `cdsp`, `slpi`, `venus` падали на `qcom_scm_pas_mem_setup` с
кодом TZ −70 (`a0 = 0xFFCFFFBA`), а загрузка zap-шейдера GPU намертво вешала
одно ядро CPU — без printk, без реакции на NMI, с последующим RCU-stall.

**Причина.** `sm8250.dtsi` несёт обобщённую карту резервной памяти, не совпадающую
с этим аппаратом. У Xiaomi область `removed_mem` больше: `0xaf00000` против
`0x5300000`, и на эту разницу — ровно `0x5c00000` — сдвинуто всё, что лежит следом.
Наши прошивки сопроцессоров раскладывались внутрь чужой памяти, защищённой
TrustZone: отсюда и отказ `mem_setup`, и мгновенная смерть ядра на записи.

| область | было (mainline) | стало (сток) |
|---|---|---|
| `removed_mem` | `0x80b00000 + 0x5300000` | `0x80b00000 + 0xaf00000` |
| `gpu_mem` (zap) | `0x8681a000` | `0x8c41a000` |
| `video_mem` | `0x86e00000` | `0x8ca00000` |
| `cdsp_mem` | `0x87800000` | `0x8d400000` |
| `slpi_mem` | `0x88c00000` | `0x8e800000` |
| `adsp_mem` | `0x8a100000` | `0x91700000` |

Размеры везде совпадали и до правки — расходились только адреса.

**Что сделано.** В `sm8250.dtsi` четырнадцать областей переведены на стоковые
адреса. Из `sm8250-xiaomi-alioth.dts` убраны четыре узла (`slpi_mem`, `adsp_mem`,
`spss_mem`, `cdsp_secure_heap`), дублировавшие метки dtsi, и соответствующие им
строки `/delete-node/`. Эталон — стоковый device tree, `stock_dtb0.dtb`;
разбирается через `dtc -I dtb -O dts`.

**Как искали.** Пошаговые метки `GMUTRACE` в `a6xx_gmu.c`, `a6xx_gpu.c`,
`adreno_gpu.c` и `mdt_loader.c`. **Их нужно убрать** — диагностика своё отработала.
По дороге закрыты три ложные версии: прошивки GMU грузятся нормально (запрет из
старого раздела 7 держался на неверном диагнозе), SHM bridge ни при чём, cpuidle
проверен с `cpuidle.off=1` и тоже ни при чём.

### Что понадобилось сверх карты памяти

**Звук.** Машинный драйвер `sound/soc/qcom/sm8250.c` звал только
`snd_soc_dai_set_sysclk` для кодека, а она у CS35L41 настраивает лишь монитор
частоты. Опорную частоту PLL программирует обработчик уровня компонента, и без
него оба усилителя отваливались с `Enable(1) failed: -110`. Добавлен вызов
`snd_soc_component_set_sysclk(..., CS35L41_CLKID_SCLK, 0, TDM_BCLK_RATE,
SND_SOC_CLOCK_IN)`; заодно проверяются коды возврата, которые раньше терялись.
Признак успеха — регистр `PLL_CLK_CTRL` (0x2C04) читается как `0x670`
вместо `0x10`. Маршрут `TERT_TDM_RX_0 Audio Mixer MultiMedia1` включается через
`alsactl`, состояние сохранено в `/var/lib/alsa/asound.state`.

**SLPI.** В `include/linux/soc/qcom/pdr.h` предел `SERVREG_NAME_LENGTH` поднят
с 64 до 128: прошивка Xiaomi присылает более длинные пути, и ядро роняло разбор
с `qmi_decode_string_elem: String len 128 >= Max Len 65`. Ошибки ушли, но сам
SLPI это не спасло — см. раздел 7.

**Камеры** заработали сами после правки карты памяти. Проверено съёмкой:
`s5k5e9` отдаёт 2592×1944 в `pgAA` (SGRBG10 упакованный) через
`msm_csiphy0 → msm_csid0 → msm_vfe0_rdi0 → /dev/video0`; скрипт сборки тракта
лежит на аппарате в `/root/cam.sh`. Важно: формат узла захвата должен совпадать
с порядком байт датчика, иначе `STREAMON` отдаёт `broken pipe`.

## 6. Попытка загрузиться через ABL (более не актуально)

Затевалось ради версии «виновата сторонняя UEFI». Версия оказалась неверной:
причина была в device tree, а не в загрузчике. Разбор оставлен как справка.


Чтобы проверить версию выше, собирали образы для штатного загрузчика.
**Все отвергнуты**, ABL молча уходит в fastboot, на экран не пишет ничего.

Перепробовано: формат заголовка 2 и 3; с AVB-подписью и без;
с ramdisk (минимальным и штатным) и без; дерево в секции образа и приклеенное
к ядру; идентификаторы платы как у стока (`qcom,msm-id` для трёх ревизий kona,
`qcom,board-id = <0 0>`). Слот `a` исправен, счётчик попыток не исчерпан,
AVB при разлоченном загрузчике не проверяется (`Device is unlocked, Skipping
boot verification` — строка из самого ABL).

Ramoops после такой попытки пуст — значит **ABL до запуска ядра не доходит**,
бракует образ раньше.

### Разбор ABL (не закончен)

```
abl.elf → abl_payload.bin → abl_inner.bin (LZMA, 0.95 MB)
        → abl_ll.pe (PE32+ AArch64, 946 KB) → abl_text.bin
```

Строки-якоря сопоставлены с кодом:

| адрес | строка |
|---|---|
| `0x9524` | `Invalid vendor_boot partition. Skipping` |
| `0x16fdc` | `Error: Device Tree blob not found` |
| `0x17484` | `Single appended DTB found` |
| `0x19b60` | `Best match DTB tags` |

Расшифровано:

- годность `vendor_boot` проверяется индексом раздела (функция `0x26e68`,
  негодно при `-1` или `≥128`) и полем `header_version` — значения 1 и 2 бракуются;
- дерево ищется по вычисленному адресу, заголовок FDT проверяется через `0x43160`,
  при неудаче — выход с `0x8000000000000004`;
- на `0x17448` идёт пересчёт, одно дерево приклеено или несколько.

**Не доведено:** откуда берётся указатель на дерево (`x25`) — он приходит
в функцию извне, нужно раскручивать вызовы вверх.

## 7. Ловушки, на которые уже наступили

**Счётчик попыток загрузки слота тратится на КАЖДОЙ загрузке**, а не только на
неудачной, и после седьмой ABL уводит аппарат в fastboot. Лечилось раньше
`fastboot set_active a`. Закрыто окончательно: в GPT-атрибутах раздела `boot_a`
(это `/dev/sde`, раздел 12) выставлен бит 54 — «слот загрузился успешно»:

```bash
sfdisk --part-attrs /dev/sde 12 "GUID:48,49,50,52,53,54"
```

Раскладка битов: 48–49 приоритет, 50 активен, 51–53 счётчик попыток, 54 успешно,
55 незагружаемый. Резервная копия таблицы — `/root/sde-gpt-backup.sfdisk` на аппарате.

**SLPI выключен намеренно.** Прошивка грузится и проходит проверку, но внутри
неё стартует пользовательский домен `sensor_process`, ждущий закрытый демон
датчиков Qualcomm. На mainline его нет, и сторожевой таймер прошивки роняет SLPI
каждые ~40 секунд, каждый раз заново прогоняя проверку подписи. Все датчики
движения висят за SLPI и без этого демона недоступны в любом случае, поэтому
узел переведён в `status = "disabled"`. В IIO остаются только АЦП контроллеров
питания. Чтобы вернуть — `status = "okay"` в `&slpi`.

**Тёплый сброс: отпускайте громкость сразу, как погаснет экран.** Если держать
её дальше, XBL перехватывает загрузку и уводит в fastboot. Оттуда достаточно
`fastboot reboot`, ramoops при этом выживает.

**Сторожевой таймер стирает ramoops.** `RuntimeWatchdogSec` в systemd честно
перезагружает зависший аппарат, но сброс по нему ведёт себя как долгое удержание
питания — лог пропадает. Автовосстановление и снятие лога несовместимы; сейчас
таймер выключен.

**Версия ядра.** В `.config` задано `CONFIG_LOCALVERSION="-sm8250+"` явно.
Если суффикс `+` пропадёт, каталог `/usr/lib/modules/6.15.1-sm8250+` перестанет
совпадать с `uname -r`, и **не загрузится ни один из 744 модулей** — пропадут
Wi-Fi и драйвер сопроцессоров, а система будет выглядеть зависшей.
Включён `CONFIG_MODULE_FORCE_LOAD`, чтобы в таком случае можно было догрузить
принудительно, не пересобирая модули.

**`fastboot boot` этот загрузчик отклоняет** («Not Found»). TWRP приходится
именно прошивать в `boot`, а потом возвращать UEFI.

**Клон ядра на APFS** теряет парные по регистру файлы в `netfilter`
(`xt_DSCP.c` против `xt_dscp.c` и ещё три). Проявляется на середине сборки как
`No rule to make target`. Эти четыре цели отключены в конфиге.

## 8. Как снять лог зависания

Единственный способ увидеть раннюю загрузку — ramoops. В device tree добавлен узел
`ramoops@b0000000` с геометрией, **совпадающей с Android** (4 MB, console 2 MB,
pmsg 2 MB, record 0) — именно поэтому лог потом читается из TWRP.

1. Перед опытом: `rm /sys/fs/pstore/*`
2. После зависания — **тёплый сброс**: питание + громкость вниз прямо из зависшего
   состояния. Долгое удержание одного питания обнуляет память и лог пропадёт.
3. Прошить TWRP: `fastboot flash boot skkk.img`
4. Читать `/sys/fs/pstore/console-ramoops-0` — Android-ядро видит ту же область.
5. Вернуть UEFI: `fastboot flash boot uefi/Mu-alioth-0.img`

## 10. Графическая оболочка и звук

**Оболочка.** Plasma Mobile 6.7.4 из репозитория, вход автоматический под
пользователем `phone` (пароль `123456`) через `sddm`, сессия `plasma-mobile`.
Установлены `plasma-settings`, `konsole`, `angelfish`, `kclock`, `koko`,
`discover`, `plasma-systemmonitor`. Mesa даёт `FD650`, OpenGL 4.6 и ES 3.2.

**Пакет пришлось пересобрать.** `plasma-mobile` подключает приватные заголовки
`QtWaylandClient`, у которых нет двоичной совместимости между сборками Qt.
Пакет собран 5 августа, `qt6-base` пересобран 28-го — смещения полей уехали, и
в `ShellUtil::setInputRegion` единственное место без проверки на ноль
(`waylandDisplay->compositor()->object()`) стало падать. Оболочка стартовала,
рисовала экран и умирала по SIGSEGV. Пересборка под установленный Qt лечит:

```bash
# на аппарате, исходники в /root/plasma-mobile-6.7.4
cmake -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=/usr -DBUILD_TESTING=OFF
cmake --build build -j8 && cmake --install build
```

Сборка занимает минут пятнадцать на самом телефоне. **Ловушка:** установка
прописывает в `/usr/share/wayland-sessions/plasma-mobile.desktop` путь
`/usr/lib/libexec/plasma-dbus-run-session-if-needed`, которого в этой системе
нет — сессия после этого перезапускается по десять раз в секунду. Путь надо
поправить на `/usr/lib/plasma-dbus-run-session-if-needed`. При обновлении
пакета из репозитория падение вернётся, пока Arch ARM не пересоберёт его.

**Звук потребовал трёх правок.**

1. Машинный драйвер `sound/soc/qcom/sm8250.c` звал только
   `snd_soc_dai_set_sysclk`, которая у CS35L41 настраивает лишь монитор частоты.
   Опорную частоту PLL программирует обработчик уровня компонента — добавлен
   вызов `snd_soc_component_set_sysclk(..., CS35L41_CLKID_SCLK, ...)`. Без него
   усилители не включались вовсе: `Enable(1) failed: -110`. Проверка:
   регистр `PLL_CLK_CTRL` (0x2C04) должен читаться как `0x670`, а не `0x10`.
2. Для карты не было описания ALSA UCM, и PipeWire отдавал заглушку вместо
   динамика. Написано `/usr/share/alsa/ucm2/Qualcomm/sm8250/HiFi-alioth.conf`
   плюс ссылки в `conf.d/sm8250/`. **Громкость усилителей в последовательности
   выключения трогать нельзя** — иначе после первого перехода тракта в покой
   она остаётся нулевой и звук пропадает без всяких ошибок.
3. Драйвер `q6asm` формально принимает режим MMAP, но DMA не запускает:
   состояние PCM остаётся `RUNNING`, а `hw_ptr` замирает намертво. Это давало
   тишину и `IO Error` в настройках KDE. Отключено в
   `/etc/wireplumber/wireplumber.conf.d/51-alsa-alioth.conf`.

Быстрая проверка тракта, минуя PipeWire:
`aplay -D plughw:0,0 /usr/share/sounds/alsa/Front_Center.wav`.

**Регулировка громкости потребовала правки `plasma-pa`.** Ползунок в оболочке
не двигался, а качелька на корпусе только показывала шторку. Причина в
`src/preferreddevice.cpp`: класс заполняет своё поле исключительно по сигналу
`defaultSinkChanged`, а под `pipewire-pulse` тот приходит раньше, чем выход
попадает в список, и `Server::defaultSink()` навсегда отдаёт пустоту. Оболочка
же блокирует ползунок по `enabled: model.VolumeWritable`, которое у пустого
объекта не определено. Наложенный патч (исходники в `/root/plasma-pa-6.7.4`):
пересчитывать ещё и по `Context::sinkAdded`/`sourceAdded`, вызывать пересчёт
в конструкторе и брать первое устройство из списка, если сервер имя не
сопоставил. После установки нужно перезапустить не только `plasmashell`, но и
`plasma-kded6` — кнопки громкости обрабатывает модуль `audioshortcutsservice`
внутри него.

**Оба патча (`plasma-mobile` и `plasma-pa`) затрутся при обновлении пакетов.**
Исходники и каталоги сборки лежат на аппарате в `/root`, пересобрать можно теми
же тремя командами.

**Профиль карты должен быть HiFi.** В настройках KDE рядом лежит `Pro Audio` —
он отдаёт сырые устройства без маршрутизации и молчит; если звук пропал
целиком, первым делом проверить `pactl list cards | grep "Active Profile"`.

**Сеть.** Wi-Fi переведён на NetworkManager, иначе аплет Plasma его не видит.
`usb0` намеренно оставлен за `systemd-networkd`
(`/etc/NetworkManager/conf.d/10-unmanaged.conf`) — это канал управления,
отдавать его нельзя.

**Камеры и звук конфликтуют.** PipeWire перечислял узлы `camss` как
видеоустройства и постоянно будил привод автофокуса `dw9800`, который не
отвечает по шине CCI (`Failed to init VCM: -110`) — слышался ритмичный треск
у блока камер. Опрос отключён в
`/etc/wireplumber/wireplumber.conf.d/50-no-cameras.conf`. Если камеры
понадобятся приложениям через PipeWire, файл надо убрать и разбираться с CCI.

## 12. Модем: SDX55 по PCIe (01.09.2026, работа не закончена)

### 12.1 Главное: модема внутри SoC нет

Snapdragon 870 не содержит модема. В аппарате стоит **отдельная микросхема
Qualcomm SDX55** (Snapdragon X55 5G), подключённая по **PCIe2** (`pcie@1c10000`,
`0002:01:00.0`, `17cb:0306`, подсистема `17cb:010c`). Общение — по **MHI**.

Доказательства: в разделе `modem_a` нет MPSS, зато есть каталог `image/sdx55m/`
с полным набором образов чужого чипа (`sbl1.mbn`, `tz.mbn`, `hyp.mbn`, `aop.mbn`,
`apps.mbn`, `devcfg.mbn`, `apdp.mbn`, `acdb.mbn`, `sec.elf`, `xbl_cfg.elf`,
`mdmddr.mbn`, `multi_image*.mbn`, `efs1..3.bin`, `qdsp6sw.mbn` — 84 МБ);
в стоковом дереве узел `qcom,mdm0 { compatible = "qcom,ext-sdx55m"; }` и алиас
`mhi-netdev0 = ".../qcom,pcie@1c10000/pcie2_rp/qcom,mhi@0/..."`; в mainline
PHY третьего контроллера называется `qcom,sm8250-qmp-modem-pcie-phy`.

Следствия: `remoteproc_mpss` не нужен вообще; `rmtfs` не нужен (EFS у SDX55
свой); **IPA не является обязательной** — это ускоритель, а данные можно гонять
через каналы MHI `IP_HW0`/`IP_SW0` силами CPU.

Модем **flashless**: своей флеш-памяти нет, весь загрузочный набор подаёт
процессор. Схема: PBL принимает `sbl1.mbn` через BHI → SBL запрашивает
остальное по протоколу **Sahara** поверх MHI-каналов 2/3 (только в EE=SBL).

### 12.3 Правки в дереве устройств

`sm8250-xiaomi-alioth.dts`:

```
&pcie2 {
	pinctrl-0 = <&pcie2_default_state &mdm2ap_default &ap2mdm_default>;
	status = "okay";
};
&pcie2_phy {
	vdda-phy-supply = <&vreg_l5a_0p88>;
	vdda-pll-supply = <&vreg_l9a_1p2>;
	status = "okay";

```
плюс в `&tlmm` состояния `ap2mdm_default` (gpio56, 57) и `mdm2ap_default`
(gpio1, 3). Образец — `sm8250-sony-xperia-edo.dtsi`: Xperia 1 II сделан по той
же референс-схеме и уже включает pcie2 в mainline.

`sm8250.dtsi`, узел `pcie2`: добавлено девятое прерывание
`<GIC_SPI 236 IRQ_TYPE_LEVEL_HIGH>` с именем **`global`**. Без него
`pcie-qcom` не выставляет `use_linkup_irq` и не обрабатывает событие
«линк поднялся» (`qcom_pcie_global_irq_thread` → `pci_rescan_bus`). Номер взят
из стокового дерева: в `interrupt-map` узла pcie2 ребёнок 0 (`int_global_int`)
ведёт на SPI 236, а рёбра 1–4 (`int_a`..`int_d`) — на 290/415/416/417, что
совпадает с mainline и подтверждает соответствие.

### 12.4 Правки в ядре

`drivers/bus/mhi/host/pci_generic.c`

- Новый `mhi_qcom_sdx55_fusion_info` для подсистемы `17cb:010c` (раньше эта
  запись вела на `mhi_foxconn_sdx55_info`, у которого **нет `.fw`**, отчего
  драйвер падал с «No firmware image defined»). Задано
  `.fw = "qcom/sdx55m/sbl1.mbn"`, `.sbl_bounce = true`, `timeout_ms = 120000`.
- **Набор колец обязан быть минимальным.** Пока в конфигурации были аппаратные
  кольца событий (`MHI_EVENT_CONFIG_HW_DATA`, то есть `NHWER > 0` в `MHICFG`),
  модем через ~100 мс после записи M0 **ронял линк PCIe** (AER: `SDES+`
  Surprise Down, конфиг читается как `ffffffff`, обратно не поднимается).
  С одним управляющим кольцом линк живёт. Это была самая дорогая находка дня.
- Управляющее кольцо посажено на **вектор MSI 0** (`.irq = 0`, общий с BHI):
  события с вектора 1 и выше до хоста не доходят вовсе.

`drivers/bus/mhi/host/{pm,boot,init,main}.c`, `include/linux/mhi.h`

- `MHI_POWER_UP_CAPABLE` расширен на `MHI_EE_SBL` — иначе повторная загрузка
  драйвера на уже стартовавшем модеме отбивается («SECONDARY BOOTLOADER is not
  a valid EE for power on»), и для каждой попытки нужна перезагрузка.
- `mhi_ready_state_transition()`: после перевода в M0 перечитывается EE и, если
  устройство уже в SBL, переход **инициируется вручную**. Событие смены EE этот
  модем не присылает (кольцо ещё не живо в момент смены), и штатный автомат
  вечно ждёт.
- Флаг `wait_for_sbl`: после приёма образа по BHI ждём, пока устройство
  вернётся и осядет в EE=SBL (примерно 300 мс), и только потом трогаем MMIO.
- Флаг `poll_events` + `mhi_ev_poll_work`: кольца событий опрашиваются раз в
  2 мс, потому что **MSI от модема не приходят** (счётчик прерываний ровно 0,
  события при этом в кольцо ложатся). Без опроса `mhi_device_get_sync()` в
  `mhi_driver_probe` висит весь таймаут и канал не стартует.

`drivers/net/wwan/mhi_wwan_ctrl.c`

- В таблицу добавлен канал `SAHARA` (тип порта `WWAN_PORT_FIREHOSE`), иначе
  канал никем не подхватывается.
- `MHI_WWAN_MAX_MTU` снижен с `0x8000` до `0x400`. Модем в `HELLO` объявляет
  `max_length = 1024`; при 32 КБ приёмных буферах обмен разваливается на
  `MHI_EV_CC_BAD_TRE` по каналу 3. Это правка «в лоб» — правильнее сделать MTU
  свойством канала, иначе страдают MBIM/QMI.

**Окно SMMU по 0x94000000.** Параметр модуля `sdx_win=1` (по умолчанию 0)
отображает 2 МБ собственной памяти по фиксированной IOVA `0x94000000` в домене
устройства через `iommu_map()`. **Без него модем не грузится вообще** — см. 12.5.
Страница заполняется узором `0xa5a5dead ^ смещение`, содержимое видно в
`/sys/kernel/debug/mhi_sdx_win`, а при выгрузке в dmesg печатается, что именно
модем туда записал. Второй параметр, `sdx_dma_bits`, переопределяет ширину
DMA-маски; он оказался тупиковым (12.5), оставлен на всякий случай. Оба
действуют только на устройства с `sbl_bounce`.

`iommu_set_fault_handler()` на этом домене использовать нельзя: в 6.15 она
требует `cookie_type == IOMMU_COOKIE_NONE`, а у DMA-домена он иной, и вызов
даёт `WARNING` в `drivers/iommu/iommu.c:1991`, ничего не установив.

**Отладочная печать `MHIDBG`** осталась в `pm.c`, `boot.c`, `main.c`,
`pci_generic.c` — убрать вместе с `GMUTRACE`.

### 12.5 Разбор фолта SMMU (историческое, 01.09 днём)

**Где стоим сейчас — 12.13 и 12.15.** Этот раздел оставлен как разбор фолта
по `0x9403f000` и списка опровергнутых тогда версий.

**Фолт SMMU разобран и закрыт.** Модем пишет по `0x9403f000` **одно 32-битное
слово** со значением `0x00000002` — и больше ничего. Проверено зондом: 2 МБ
своей памяти отображены по IOVA `0x94000000`, страница залита узором, после
прогона изменилось ровно одно слово:

```
MHIDBG sdx_win: 1 words written, iova 0x9403f000..0x9403f003
MHIDBG sdx_win: 00000000: 00000002 a5a62ea9 a5a62ea5 a5a62ea1
```

Похоже на мейлбокс состояния, который прошивка модема держит по зашитому
адресу. Смысл значения не выяснен (2 = EE AMSS? стадия загрузки?).

Что из прежних выводов оказалось неверным:

- **Обрыв 84 МБ не был связан с фолтом.** Фолт прилетает уже на стадии PBL,
  через ~275 мс после probe, задолго до Sahara. С отображённым окном фолтов нет
  ни одного, и `qdsp6sw.mbn` уходит целиком (84 018 040 из 84 021 388 байт;
  разница — куски, которые модем сам пропускает) со статусом 0.
- **Адрес не выводится из наших.** Прогон с `sdx_dma_bits=30` увёл все наши
  IOVA из `0xffff****` вниз, под `0x40000000` (туда, где лежит стоковый пул
  `mhi_0_iommu_group`, `qcom,iommu-dma-addr-pool = <0x20000000 0x1fffffff>`), —
  адрес фолта не сдвинулся ни на бит. Заодно выяснилось, что буферы ниже
  `0x40000000` модему не годятся вовсе: канал умирает сразу после `HELLO`.
  Стоковый пул воспроизводить не надо.
- В стоковом дереве у `qcom,mhi@0` **нет** `memory-region` — окна по этому
  адресу Android модему тоже не даёт. Чем он там пользуется — неясно.

**Обмен Sahara проходит целиком.** Порядок: `qdsp6sw` → `DONE_RESP` со
статусом 0 → `HELLO` с `mode=1` → `apps.mbn` (слот 6) → `DONE_RESP` со
статусом 1. Значения `image_tx_status` те же, что у `SAHARA_MODE_*`:
**0 = IMAGE_TX_PENDING, 1 = IMAGE_TX_COMPLETE**. То есть единица в конце
означает «образы кончились, всё принято», а не ошибку.

**Новая стена — модем не уходит из SBL.** Устойчивая картина, снятая четырьмя
прогонами подряд: Sahara проходит целиком, модем один раз пишет `0x00000002`
по `0x9403f000`, остаётся в `EE=1` с живым линком 8.0 GT/s x2 и больше не
делает ничего. Через 30 с `mhi_sync_power_up()` отваливается с `-110`, MHI
рушит канал SAHARA (он существует только в EE=SBL), сервер видит EIO.

| прогон | адрес записи | значение | фолты SMMU | линк | EE |
|---|---|---|---|---|---|
| 1–4 | `0x9403f000` | `0x00000002` | 0 | 8.0 GT/s x2 | SBL |

Две аномалии, каждая по одному разу на десяток прогонов, — **выбросы**, не
закономерность, и строить на них выводы нельзя:

- Один раз модем записал двойку по `0x94000000`, а не по `0x9403f000`.
- Один раз (и только раз) он через 2,8 с после конца обмена записал в мейлбокс
  `0` и уронил PCIe: линк ушёл в `2.5 GT/s x1`, что есть значение LNKSTA по
  умолчанию при отсутствии линка, а не медленный линк. В AER рутового
  комплекса при этом защёлкнулись `UESta: SDES+ CmpltTO+`. В dmesg тихо
  потому, что mainline размаскирует в `PARF_INT_ALL_MASK` только
  `PARF_INT_ALL_LINK_UP` (бит 13) и `PARF_INT_MSI_DEV_0_7`; события link-down
  Linux не получает вовсе.

Инициализация PCIe при этом в порядке: `perst-gpios = <&tlmm 85 GPIO_ACTIVE_LOW>`
есть в `sm8250.dtsi:2448`, пины 85/86/87 описаны в `pcie2_default_state`,
прерывание link-up размаскировано один раз при probe и остаётся armed. То есть
если бы устройство переобучало линк, мы бы получили `pci_rescan_bus`.

**Что такое 0x9403f000: это адрес MSI-доорбелла, а не мейлбокс.** Разобрано
по `sbl1.mbn` в Ghidra (ARM32, база `0x14817000`). В SBL лежит свой PCIe-стек
(`pcie_core.c`, `pcie.c`, `pcie_i.c`). Цепочка:

- `FUN_1483212c` читает регистры по смещениям `0x50/0x54/0x58/0x5c` от DBI-базы
  с маской `0x10000` и полем `0x700000 >> 20`. Это **MSI capability**:
  контрольное слово (бит 16 — MSI Enable, биты 20–22 — Multiple Message
  Enable), Message Address, Message Upper Address, Message Data.
- `FUN_14832990` кладёт прочитанный Message Address в контекст по `+0x8c/+0x90`
  и строит из него конфиг исходящего региона ATU размером `0x1000`.
- `FUN_148323a8` программирует iATU по схеме DWC: `+0x08/+0x0c` — база,
  `+0x10` — предел (`база + размер - 1`), `+0x14/+0x18` — **target**,
  `+0x04` — control с битом разрешения `0x80000000`.

То есть запись `0x00000002` по `0x9403f000` — это модем **выставляет MSI**.
Адрес прописало ему наше же ядро, значение — номер вектора.

**Почему он не проходит.** `pcie-designware-host.c` берёт доорбелл так:

```c
msi_vaddr = dmam_alloc_coherent(dev, sizeof(u64), &pp->msi_data, GFP_KERNEL);
```

где `dev` — сам контроллер `1c10000.pcie`. У его узла нет `iommus`, мастером за
SMMU он не является, поэтому возвращается **физический** адрес. А конечное
устройство за SMMU сидит — SID `0x1d01` из `iommu-map` узла pcie2 — и пишет по
этому адресу как по IOVA. Трансляции для него нет, SMMU обращение режет.

Одним этим объясняется сразу три вещи, которые считались разными:

1. Фолт по постоянному адресу. Адрес постоянный, потому что `dmam_alloc_coherent`
   при детерминированном порядке загрузки отдаёт одну и ту же страницу.
2. **MSI не доходят вовсе** (12.4). Они и не могут: запись режется SMMU.
   Опрос колец раз в 2 мс — это лечение симптома.
3. Падение линка при аппаратных кольцах событий (12.4). Больше колец — больше
   MSI — больше зарезанных обращений.

**Проверено на железе.** `msiprobe.py` (на аппарате, только чтение) читает
MSI capability модема из конфигурационного пространства и рядом — то, что стоит
у контроллера в DBI по `PCIE_MSI_ADDR_LO/HI` (`0x820/0x824`, DBI у pcie2 по
`0x64000000`):

```
endpoint MSI cap at 0x50            <- ровно те смещения, что читает SBL
root complex is listening on 0x9403f000
```

Смещение capability `0x50` совпадает с тем, что видно в дизассемблере, а адрес —
с адресом из фолта. Диагноз подтверждён.

**Адрес доорбелла не постоянен.** В разных загрузках `pp->msi_data` оказывался
то `0x9403f000`, то `0x94000000`. Этим объясняются прежние «выбросы»: прогон, где
модем писал по `0x94000000`, был просто загрузкой с другим доорбеллом.

**Параметр `sdx_msi=1`** отображает страницу доорбелла в домен устройства один в
один (IOVA = PA, адрес читается из capability после `pci_alloc_irq_vectors`).
Результат: фолты SMMU исчезают полностью, и обмен Sahara проходит целиком
**без** `sdx_win` — то есть окно никогда и не было нужно, оно лишь случайно
накрывало страницу доорбелла.

**Но прерывания от этого не появились.** Проверено параметром `sdx_poll=0`,
который выключает программный опрос колец: модем тогда не уходит даже из PBL,
канал SAHARA не поднимается (`mhi_wwan_ctrl ... error -5`), лог Sahara пуст.
Значит запись теперь просто ложится в память, а корневой комплекс её
по-прежнему не перехватывает.

**Чем pcie2 отличается от pcie0, где MSI работают.** Ничем из очевидного:

```
pcie0  ADDR=0x94000000  ENABLE=0xffffffff  MASK=0xfffffffe  STATUS=0
pcie2  ADDR=0x9403f000  ENABLE=0xffffffff  MASK=0xfffffffe  STATUS=0
```

`iommu-map` у обоих одной формы, конечное устройство отображено в SMMU и там
(`0x1c01`), и там (`0x1d01`), а у Wi-Fi прерывания идут. Маска `0xfffffffe`
стоит на **работающем** контроллере тоже, так что с ней запись «векторы с
первого не доходят» не связана.

Единственное найденное различие в конфигурации — **прерывание `global`**,
которое мы сами добавили в pcie2 ради обработки link-up (12.3). Из-за него
`qcom_pcie_probe()` пишет `PARF_INT_ALL_MASK = PARF_INT_ALL_LINK_UP |
PARF_INT_MSI_DEV_0_7`, чего у pcie0 не происходит вовсе. Проверить это дёшево:
убрать `global` из дерева и посмотреть, не пойдут ли MSI. Цена — потеря
автоматической обработки link-up, которой мы фактически не пользуемся.

**Ответ нашёлся в исходниках Xiaomi** (`xiaomi-alioth-oss`, ветка `alioth-r-oss`,
поверхностный клон в каталоге проекта). Файл
`drivers/pci/controller/pci-msm-msi.c`, драйвер того самого `qcom,pci-msi`:

```c
/* msm_msi_domain_prepare() - на каждое устройство-клиент */
client->msi_addr = dma_map_resource(client->dev, msi->msi_addr,
                                    PAGE_SIZE, DMA_FROM_DEVICE, 0);

/* msm_msi_irq_compose_msi_msg() */
msg->address_lo = lower_32_bits(client->msi_addr);  /* IOVA, не физический */
msg->data       = irqd_to_hwirq(parent_data);       /* номер линии GIC */
```

Схема у стока принципиально другая:

- доорбелл — **аппаратный регистр** по `0x17a10040` (он же в `reg` узла
  `qcom,pcie2_msi`), а не страница памяти;
- он отображается `dma_map_resource()` в домен IOMMU **каждого** устройства, и в
  MSI capability уезжает полученная IOVA;
- каждый вектор — своя выделенная линия GIC, отсюда 32 SPI (`0x340`–`0x35f`) в
  узле `pcie2_msi`, а `msg->data` несёт номер этой линии.

Mainline не делает ничего из этого: `dw_pcie_msi_host_init()` выделяет страницу
памяти на самом контроллере, получает **физический** адрес (контроллер не мастер
за SMMU) и пишет его в capability всем устройствам, не отображая никуда. Отсюда
и фолт.

Этим же объясняется, почему `sdx_msi` убрал фолт, но не дал прерываний:
отображена была `pp->msi_data`, то есть обычная страница памяти, а не регистр.
Запись стала попадать в память, но латчить её там некому. Путь mainline через
встроенный MSI DesignWare на этой шине, судя по всему, нерабочий в принципе —
и правка внутри него смысла не имеет.

**Схема проверена на железе и работает.** Параметр `sdx_bell=1`: отображает
регистр `0x17a10040` в домен модема через `dma_map_resource()`, занимает
GIC SPI `0x340` обычным `request_irq()` и переписывает MSI capability модема —
адрес на полученную IOVA, `data` на hwirq линии. Результат:

```
MHIDBG sdx_bell: doorbell 0x17a10040 -> iova 0x00000000fffff000,
                 SPI 0x340 = virq 304 hwirq 864, capability rewritten
MHIDBG sdx_bell: rang, hit 1
MHIDBG sdx_bell: rang, hit 2
```

Два настоящих прерывания от модема. Адрес `0xfffff000` — это IOVA, не
физический: модем звонит по переведённому адресу, SMMU превращает его в
настоящий, кнопка нажимается. Именно поэтому путь mainline здесь и не работает —
он выдаёт устройству сырой физический адрес обычной страницы памяти.

В этом прогоне сам обмен не пошёл, модем остался в PBL: зонд перехватывает
единственный вектор MSI себе в пробный обработчик, и MHI своих прерываний не
получает. Для проверки «доходит ли звонок» это неважно.

**Что делать дальше.** Оформить это как положено: контроллер прерываний в духе
`pci-msm-msi.c` (416 строк), владеющий всеми 32 линиями (`0x340`–`0x35f`,
номера из стокового узла `pcie2_msi`), выдающий каждому устройству свою IOVA на
доорбелл и раздающий векторы штатно, — вместо того чтобы отбирать их у MHI.
Тогда `poll_events` станет не нужен. Это отдельная работа со своим разбором:
она про PCIe, а не про модем, и заденет все три шины.

**Но с застреванием в SBL это, скорее всего, не связано** — при работающем
опросе колец события до модема доходят, а он всё равно не уходит из SBL.
Прежде чем вкладываться в контроллер, стоит дочитать в исходниках Xiaomi
`drivers/bus/mhi/controllers/mhi_qcom.c`, `mhi_arch_qcom.c` и esoc: там вся
последовательность подъёма модема, включая то, чего он ждёт после Sahara.


**Рукопожатие esoc.** Стоковый узел `qcom,mdm0` называет пины:
`ap2mdm-status` = tlmm 56, `ap2mdm-errfatal` = tlmm 57, `mdm2ap-status` = tlmm 3,
`mdm2ap-errfatal` = tlmm 1. В нашем дереве они только сконфигурированы через
pinctrl, никто их не ведёт. Проверено: удержание `56=1, 57=0` через
`gpioset -c gpiochip3` весь прогон **ничего не меняет** — модем и без этого
доходит до конца Sahara и сам уходит в сброс. Поднятие линии постфактум, когда
модем уже сидит в SBL, тоже ни на что не влияет. Пины свободны (`gpiochip3` =
`f100000.pinctrl`, 181 линия), драйвер их не занимает.

**Инструменты на аппарате** (оба только на чтение):

| файл | что делает |
|---|---|
| `/root/mdmwatch.py` | раз в 2 мс читает `BHI_EXECENV`, `BHI_STATUS`, `MHISTATUS` из `resource0` плюс скорость и ширину линка; печатает только изменения. Ждёт не успешного mmap, а осмысленного указателя BHI: до `mhi_pci_claim()` BAR не назначен и читается как `0xffffffff` |
| `/root/winwatch.py` | раз в 20 мс читает слово по смещению `0x3f000` в `/sys/kernel/debug/mhi_sdx_win`, то есть мейлбокс модема живьём |

`timeout_ms` в `mhi_qcom_sdx55_fusion_config` снижен со 120 до **30 с**. Ниже
нельзя: `mhi_sync_power_up()` ждёт его же, пока Sahara льёт 84 МБ, а это ~15 с.

**Снимать трансляцию по-прежнему нельзя** — проба с закомментированным
`iommu-map` у pcie2 кончилась записью в живую DDR и падением системы. Дерево
в безопасном виде и не менялось: всё лечится со стороны драйвера.

Второй нерешённый вопрос — **почему не доходят MSI**. Сейчас это обойдено
опросом раз в 2 мс, что для 84 МБ терпимо (образ уходит за 15 с), но для данных
не годится.

### 12.6 Что взято из исходников Xiaomi

Дерево `xiaomi-alioth-oss` (ветка `alioth-r-oss`, поверхностный клон, 1.2 ГБ)
лежит в каталоге проекта. Оттуда разобран путь подъёма модема.

**Структурно мы совпадаем со стоком.** В их `firmware_table` для `dev_id 0x306`
одна строка — `sdx55m/sbl1.mbn`; флаг `fbc_download`, включающий заливку образа
через BHIe, не выставляется нигде во всём `drivers/bus/mhi`; Sahara у них тоже
в userspace (в ядре канал виден только через `mhi_uci.c`). После образов модем
никто не подталкивает: `ESOC_IMG_XFER_DONE` — лишь уведомление, дальше esoc
ждёт, когда модем сам поднимет `MDM2AP_STATUS`.

**Рукопожатие esoc обязательно.** `mdm4x_do_first_power_on()`:

```c
mdm_toggle_soft_reset(mdm, false);   /* тёплый сброс через SPMI */
msleep(150);
gpio_direction_output(MDM_GPIO(mdm, AP2MDM_STATUS), 1);
... esoc_clink_queue_request(ESOC_REQ_IMG, mdm->esoc);
```

Проверено серией из шести прогонов, разделение чистое:

| | 1 | 2 | 3 |
|---|---|---|---|
| `ap2mdm_status = 1` удержан (tlmm 56) | 2.5 x1 | 2.5 x1 | 2.5 x1 |
| линия не тронута | 8.0 x2 | 8.0 x2 | 8.0 x2 |

`2.5 GT/s x1` — это значение LNKSTA при отсутствии линка. То есть **с поднятой
линией модем уходит из SBL** (и роняет линк, как и положено при перезапуске),
без неё стоит вечно. Раннее заключение «esoc ни при чём» было построено на
одном прогоне и неверно.

**Канал лога загрузчика.** Стоковое дерево описывает `mhi_chan@25`, метка `BL`,
device→host, только в `EE=SBL`, `auto-queue` + `auto-start`; SBL льёт туда
обычный текст, а `mhi_bl_driver` в `mhi_arch_qcom.c` складывает его в IPC-лог.
В mainline канала нет вовсе — поэтому мы за весь день не увидели от SBL ни
слова. Перенесено в `pci_generic.c`: макрос `MHI_CHANNEL_CONFIG_DL_SBL_AUTOQUEUE`,
канал 25 в конфигурации `qcom-sdx55m-fusion`, клиентский драйвер `sdx_bl_driver`,
пишущий в dmesg строкой `MHIDBG BL:`. Канал поднимается (`bootloader log
channel up`), содержимое пока приходило пустым — надо печатать длину и hex.

**Тёплый сброс модема через его PMIC.** У SDX55 свой PMIC (PMX55, «prairie») на
SPMI SID 8; в стоковом наложении это `qcom,pmxprairie@8` с блоком
`qcom,power-on@800`, помеченным `qcom,modem-reset`. Последовательность — из
`qpnp_pon_modem_pwr_off(PON_POWER_OFF_WARM_RESET)`:

```
0x863 <- 0x00 ; udelay(500) ; 0x862 <- 0x01 ; 0x863 <- 0x80 ; udelay(500) ; 0x864 <- 0xA5
```

Перенесено: в `sm8250-xiaomi-alioth.dts` добавлен узел `pmic@8` с собственным
compatible `xiaomi,alioth-modem-pmic`, в модуле — драйвер SPMI `sdx_pon_driver`
и параметр `sdx_reset` (запись в `/sys/module/mhi_pci_generic/parameters/sdx_reset`).
Работает: устройство `0-08` найдено, записи проходят, модем уходит с шины.

**Но сброс — половина инструмента.** После него линк не поднимается, устройство
читается как `ffffffff`, и вернуть его нечем: у платформенного драйвера
`qcom-pcie` нет `unbind` (`suppress_bind_attrs`), сброс функции PCI и
`Retrain Link` не помогают. Ровно та же стена, что и при собственном переходе
модема из SBL.

**Отсюда следующий шаг** — восстановление линка в самом `pcie-qcom`: размаскировать
событие link-down (сейчас в `PARF_INT_ALL_MASK` разрешены только
`PARF_INT_ALL_LINK_UP` и `PARF_INT_MSI_DEV_0_7`), по нему дёрнуть PERST
(`perst-gpios = <&tlmm 85>`), дождаться переобучения и переперечислить шину.
Это первая правка не в модуле, а в самом ядре, то есть с пересборкой `Image`.
Она нужна дважды: и чтобы сброс стал полноценным инструментом, и чтобы модем
пережил свой собственный переход в AMSS.

Каждый образ проходит `Auth Metadata`, то есть проверку подписи. **Ошибок в
подаче образов нет**, SBL честно доходит до конца и передаёт управление.

**Исправлена реальная ошибка в таблице слотов.** Лог назвал слот 29 словом
`ACDB`; у нас туда шли 512 нулей, а настоящий `acdb.mbn` (131 КБ) висел на
слоте 26. После правки образ грузится целиком, и поведение изменилось: раньше
канал `BL` жил ещё десять секунд после `SBL1, End` и умирал по нашему таймауту,
теперь модем сворачивает его через 0.27 с, то есть уходит из SBL сразу. Слот 26
в классической таблице — `SSD_KEYS`, такого файла у нас нет, туда идут нули.

**Восстановление линка сделано и работает** (`PCIEDBG`, ручной триггер
`/sys/kernel/debug/qcom-pcie-recover-N`, событие link-down размаскировано).
Порядок попыток и что из этого выяснилось:

| шаг | результат |
|---|---|
| только перезапуск LTSSM | не помогает, LTSSM залипает на `0x905` |
| цикл PERST | не помогает, `-110` |
| полный `host_deinit` + `host_init` (с перезапуском PHY) | **линк возвращается**, 8.0 GT/s x2 |

Оговорка принципиальная: работает только третий шаг, а он начинается с
`qcom_ep_reset_assert()`, то есть сбрасывает модем. Спасти уже загруженный AMSS
этим нельзя — можно только начать заново.

**Но линк оказался следствием, а не причиной.** Линия `mdm2ap_status`, которой
модем сообщает «я поднялся», не встаёт **никогда** — проверено наблюдением 96 с
после падения. `mdm2ap_errfatal` при этом тоже 0, то есть о сбое модем не
заявляет. Он просто уходит после SBL и не возвращается. У стока на этот случай
есть `mdm2ap_status_check()`: по таймауту он делает вывод, что загрузка не
удалась, и перезапускает модем тёплым сбросом.

**Открытый вопрос на тот момент:** почему после `SBL1, End` не поднимается AMSS.
**Закрыт вечером того же дня — см. 12.8:** модему не хватало объявления
поддержки масштабирования полосы, которого в mainline нет.

Что осталось непроверенным и может ещё пригодиться:

1. Полный сброс питания модема вместо тёплого (`PON_POWER_OFF_HARD_RESET`
   вместо `WARM_RESET` в `sdx_modem_warm_reset()`).
2. Образы, которые модем ни разу не запросил: `multi_image*.mbn`, `sec.elf`,
   `xbl_cfg.elf`, `apdp.mbn`, `devcfg.mbn` — часть слотов в таблице до сих пор
   угадана, а лог `BL` называет настоящие имена и позволяет сверить остальные.
3. Автоматическое восстановление (`/sys/module/pcie_qcom/parameters/auto_recover`,
   по умолчанию 0) — включать осознанно: первая версия с общей очередью работ
   намертво повесила машину, см. ниже. Теперь оно нужнее, чем было: линк падает
   уже из AMSS.

**Грабли, на которые уже наступили в этой части:**

- Восстановление нельзя вешать на системную очередь работ. `mhi_ev_poll_work()`
  опрашивает кольца оттуда же раз в 2 мс, а `mhi_sync_power_up()` без этого не
  завершается; работа восстановления блокируется на `device_lock` идущего
  probe — и они ждут друг друга. Машина висит целиком при живом сетевом стеке
  (ping идёт, ssh нет). Сейчас у восстановления своя очередь `qcom-pcie-recover`.
- У корневой шины `bus->self` равен `NULL`; читать `LNKSTA` надо через DBI
  (`dw_pcie_find_capability` + `dw_pcie_readw_dbi`), иначе Oops в обработчике.

нашей конфигурации `ee_mask = BIT(MHI_EE_AMSS)`. Их появление и есть
доказательство: раньше за весь день модем не выходил из SBL ни разу.

**Что этому предшествовало — перенос масштабирования полосы (bandwidth scaling).**
Модем объявляет эту возможность, проверено обходом списка возможностей прямо на
железе (`/root/capwalk.py`):

```
MISC(0x24) = 0x00000a20
  offset 0xa20: id=2 (TIMESYNC)   next=0xa30
  offset 0xa30: id=3 (BW_SCALE)   next=0x000   -> cfg по 0xa34
```

В mainline поддержки нет вовсе. Перенесено из downstream
(`mhi_process_bw_scale_ev_ring`, `mhi_init_bw_scale`, `MHI_ER_BW_SCALE`):

| файл | что добавлено |
|---|---|
| `drivers/bus/mhi/common.h` | `MHI_TRE_GET_EV_BW_REQ_SEQ`, обход возможностей (`MHI_MISC_OFFSET`, `MHI_CAP_*`), `MHI_BW_SCALE_*`, `MHI_BW_SCALE_SETUP`, `MHI_BW_SCALE_RESULT` |
| `include/linux/mhi.h` | `MHI_ER_BW_SCALE`, поле `sequence_num` в `mhi_link_info`, `bw_scale_db`, колбэк `bw_scale` |
| `host/init.c` | `mhi_get_capability_offset()`, `mhi_get_er_index()`, `mhi_init_bw_scale()` (вызов из `mhi_init_mmio`), маршрутизация нового типа кольца |
| `host/main.c` | `mhi_process_bw_scale_ev_ring()` |
| `host/pci_generic.c` | второе кольцо событий с `data_type = MHI_ER_BW_SCALE`, колбэк `sdx_bw_scale` |

При старте печатается `Bandwidth scaling on: cfg at 0xa34, event ring 1,
doorbell +0x6f0`. **Запросов на смену полосы модем при этом не присылал ни
одного** — то есть сработало само объявление поддержки, а не обмен. Похоже, SBL
проверяет её наличие и без неё дальше не идёт.

Оговорка: одновременно с этим впервые были переложены **все** модули разом (см.
грабли ниже), так что вклад двух изменений строго не разделён. Разделяется одним
прогоном: убрать `.data_type = MHI_ER_BW_SCALE` из конфигурации колец и
посмотреть, дойдёт ли модем до AMSS.

**Новая стена.** Через ~16 с после входа в mission mode линк падает
(`PCIEDBG link DOWN (#1)` на 61.0 против перехода на 44.9). Это уже падение из
AMSS, а не из SBL, и восстановление линка у нас есть — но автоматическое пока
выключено, см. 12.7.

**Грабли этой части, обе мои:**

- **Обработчик кольца событий работает в тасклете.** Мой колбэк `sdx_bw_scale`
  читал конфигурационное пространство PCI (`pcie_capability_read_word`), а это
  может уснуть — аппарат повис намертво. У downstream этой проблемы нет: их
  обработчик берёт `pm_mutex` и заведомо работает в процессном контексте.
  Сейчас в колбэке только печать. Реальную перестройку полосы, когда до неё
  дойдёт, надо выносить в отдельную работу.
- **Правки в `include/linux/mhi.h` меняют раскладку `struct mhi_controller`.**
  Выложил только `mhi_pci_generic.ko` и `Image` — и `ath11k` перестал
  регистрироваться (`failed to register to mhi bus, err = -22`), потому что был
  собран под старую структуру. Модули надо выкладывать **все**:
  `make modules_install` в `kbuild/modout`, затем `tar | ssh` целиком.
  Обратите внимание: `mhi_init_bw_scale()` и `mhi_process_bw_scale_ev_ring()`
  живут в **`mhi.ko`**, а не в `mhi_pci_generic.ko`.
- `tar` с макоси приносит на аппарат файлы `._*`, которые ломают `depmod`
  (`Exec format error`). После распаковки — `find /lib/modules -name "._*" -delete`.

### 12.9 Как повторить

Автозагрузка драйвера отключена (`/etc/modprobe.d/mhi-manual.conf`), чтобы модем
оставался в PBL и опыт был воспроизводим. Вся последовательность собрана в
**`/root/run_amss.sh`**: он заводит наблюдателей, службы QRTR, сервер Sahara и
сервер EFS, грузит модули в нужном порядке и живёт 120 с, складывая логи в
`/root/logs/<штамп>/` (симлинк `/root/logs/last`).

```bash
# на аппарате, после перезагрузки
setsid nohup bash /root/run_amss.sh > /root/run_amss.out 2>&1 &
```

Порядок внутри важен и именно такой:

```bash
mkdir -p /readwrite
setsid nohup /usr/bin/tqftpserv &            # службы QRTR — до модема
setsid nohup /usr/bin/pd-mapper &
modprobe qrtr_mhi                            # без него QMI не найти
modprobe mhi_wwan_ctrl                       # обязательно ДО mhi_pci_generic
setsid nohup python3 -u /root/sahara_srv.py &  # образы загрузки
setsid nohup python3 -u /root/efs_srv.py &     # NV модема, без неё он умрёт
modprobe mhi_pci_generic sdx_health=0 sdx_rpm=0
```

Через ~20 с модем в AMSS: появляются `/dev/wwan0qmi0`, `wwan0qcdm0` и
`wwan0xmmrpc0`. **Управление идёт не через `wwan0qmi0`** (он молчит всегда), а по
QRTR: модем — узел 3.

```bash
qmicli -d qrtr://3 --dms-get-ids            # IMEI
qmicli -d qrtr://3 --uim-get-slot-status    # обе SIM и их ICCID
qrtr-lookup                                 # все службы на шине с номерами узлов
cat /sys/module/mhi_pci_generic/parameters/sdx_reset   # линии esoc
python3 /root/efsdiag.py /nv/item_files 1   # файловая система модема
```

Ручки модуля `mhi_pci_generic`:

| ручка | назначение |
|---|---|
| `sdx_msi=1` | отображение страницы MSI-доорбелла; по умолчанию, без него сыплются фолты SMMU |
| `sdx_health=0` | не запускать восстановление по таймеру здоровья (он всё равно печатает, что увидел) |
| `sdx_rpm=0` | запретить автоусыпление модема |
| `sdx_data=0` | убрать каналы `IP_HW0` и их аппаратные кольца |
| `sdx_poll=0` | выключить опрос колец раз в 2 мс; проверка, дошли ли реально MSI |
| `sdx_bell=1` | увести MSI на настоящий доорбелл платформы `0x17a10040`; только для опыта |
| `sdx_dma_bits=30` | сузить окно IOVA; тупик, оставлен для истории |
| `sdx_win=1` | окно 2 МБ по IOVA `0x94000000`; больше не нужен |
| `sdx_reset` (запись) | тёплый сброс модема через его PMIC по SPMI |
| `sdx_reset` (чтение) | состояние линий рукопожатия esoc |
| `/sys/module/pcie_qcom/parameters/auto_recover` | автовосстановление линка, по умолчанию 0 |
| `/sys/kernel/debug/qcom-pcie-recover-2` (запись) | восстановить линк вручную |

**Чистый прогон = перезагрузка телефона.** Сброс модема на месте половинчатый:
запись в `sdx_reset` уводит его с шины, а линк поднимает только полное
восстановление, которое само начинается с PERST. `qmicli --dms-set-operating-mode=reset`
команду принимает, но после неё модем молчит по QMI при живом линке.

**Выкладка на аппарат.** Ядро и модули обязаны быть из одной сборки, иначе
ломается всё, что собрано с `struct mhi_controller`:

```bash
docker run --rm --platform linux/arm64 -v "$PWD":/prj debian:bookworm \
        bash /prj/kbuild/build19.sh          # Image + dtb + modules + modules_install
scp kbuild/linux/arch/arm64/boot/Image root@10.15.19.82:/efi/Image
scp kbuild/linux/arch/arm64/boot/dts/qcom/sm8250-xiaomi-alioth.dtb \
        root@10.15.19.82:/efi/
cd kbuild/modout/lib/modules/6.15.1-sm8250+ && tar czf - kernel | \
    ssh root@10.15.19.82 'cd /lib/modules/6.15.1-sm8250+ && rm -rf kernel && tar xzf -'
ssh root@10.15.19.82 'find /lib/modules -name "._*" -delete; depmod -a; sync'
ssh root@10.15.19.82 'bootctl set-oneshot 01-current.conf; systemctl reboot'
```

Прочие проверки: `python3 /root/bhi.py` печатает EE модема (0=PBL, 1=SBL,
2=AMSS) — работает только пока линк жив; `python3 /root/capwalk.py` печатает
список возможностей MHI; `python3 /root/msiprobe.py` сверяет адрес MSI;
`dmesg | grep -E "MHIDBG|PCIEDBG|EFSSRV|MDMWATCH|context fault"`.

### 12.10 Сервер Sahara

`/root/sahara_srv.py` — реализация протокола на Python поверх
`/dev/wwan0firehose0`. Выбран userspace ради скорости отладки; готовая
реализация Sahara в ядре есть — `drivers/accel/qaic/sahara.c`, её и стоит
переиспользовать, когда обмен доведён до конца.

Таблица идентификаторов образов взята из таблицы QDU100 в том же `sahara.c`
(родственный чип семейства SDX): 8=`qdsp6sw`, 16/17/20=`efs1..3`, 23=`aop`,
25=`tz`, 33=`hyp`, 34=`mdmddr`, 36/37=`multi_image*`, 38=`xbl_cfg`, 41=`devcfg`.
Там, где QDU100 подставляет `zeros_1sector.bin`, слот сохраняет исходный смысл:
40=`apdp`, 42=`sec`. Файл `zeros_1sector.bin` (512 нулей) создан вручную.

`sahara_srv.py` пишет строку прогресса на каждый мегабайт и отдельно отмечает,
когда модем прыгает через кусок образа, — иначе на 84 МБ по 1 КБ не видно, где
встали. Предыдущая версия лежит рядом как `sahara_srv.py.prev`.

Тонкости протокола, на которые наступили:
- После первого образа модем присылает `HELLO` с **mode=3** (командный режим) и
  `CMD_READY`; нужно ответить `SWITCH_MODE` в режим 0, иначе всё встаёт.
- `max_length` из `HELLO` ограничивает **командные пакеты**, но записи данных
  всё равно приходится резать по MTU канала.
- Каждый образ начинается с запроса 52 байт (заголовок ELF), дальше модем сам
  просит нужные куски по смещениям.

### 12.11 Смерть в AMSS: модем уходит сам, вероятная причина — нет канала EFS (01.09.2026, ночь)

**Итог вечера: модем умирает не от нас.** Прогон с выключенными хостовыми
«спасалками» (`sdx_health=0 sdx_rpm=0`, ручки добавлены) показал ту же смерть:

```
[45.188] Received EE event: MISSION MODE
[45.188] Bandwidth request seq 1: speed 0x1 width 0x2
[45.188] Bandwidth request seq 1 answered: ACK (0)
[45.195] port wwan0qcdm0 attached / port wwan0qmi0 attached
   ... 16.14 с, в логе про модем ни строки ...
[61.331] PCIEDBG link DOWN (#1)
[61.541] Device died: vendor=0xffff LNKSTA=0x0000 ee=2 pm_state=0x4
```

Промежуток между mission mode и обрывом линка воспроизводится: 16.14 с в одном
прогоне, 16.35 с в другом. Прежний вывод «через 16 с падает линк» был верен лишь
наполовину: `health_check` объявлял смерть и запускал восстановление, а оно уже
роняло линк. Теперь видно, что **линк рвётся сам**, и `Device died` приходит
через 0.2 с после `link DOWN` как следствие.

**Главный подозреваемый — отсутствующий канал EFS.** Это версия, а не доказанный факт: она объясняет всё наблюдаемое, но проверки ещё не было. Стоковое дерево (`stock_dtb0.dtb`, узел
`qcom,mhi@0`) перечисляет 51 канал, среди них:

```
mhi_chan@10 { label = "EFS"; }   mhi_chan@11 { label = "EFS"; }
mhi_chan@14 { label = "QMI0"; }  mhi_chan@16 { label = "QMI1"; }
mhi_chan@18 { label = "IP_CTRL"; } mhi_chan@22 { label = "TF"; }
```

У нас в `mhi_qcom_sdx55_fusion_channels[]` объявлены только SAHARA (2/3),
DIAG (4/5), QMI (14/15), IPCR (20/21) и BL (25). **EFS нет.**

Модем flashless: своей энергонезависимой памяти у него нет вовсе. Его EFS лежит
на флеше телефона — разделы `mdm1m9kefs1`, `mdm1m9kefs2`, `mdm1m9kefs3` (по 8 МБ,
внутри около 2 МБ значащих данных) и `mdm1m9kefsc`. Разделы `modemst1`, `fsg`,
`fsc` при этом пусты — они принадлежат несуществующему внутреннему модему, что
подтверждает: NV внешнего модема именно в `mdm1m9kefs*`.

По Sahara EFS **не подаётся**: заголовок стокового `efs1.bin` (512 байт) совпадает
с первыми байтами настоящего раздела, и модем сам просит из него ровно 40 байт и
говорит «достаточно». То есть Sahara отдаёт только заголовок, а содержимое модем
берёт в рантайме по каналу 10/11.

Сходится всё: EE=AMSS достигнут, каналы QMI и DIAG поднимаются, но
`mdm2ap_status` не встаёт **никогда**, `mdm2ap_errfatal` тоже 0, на QMI модем не
отвечает (проверено `qmicli`, восемь команд, все по таймауту — см. ниже), и через
фиксированные 16 с он уходит. Это не сбой связи, а незавершённая загрузка: без NV
модем не может подняться и по таймауту сбрасывается.

**Проверка QMI (`/root/qmiprobe.sh`).** В окно жизни модема запускаются
`--dms-get-ids`, `--dms-get-model`, `--uim-get-card-status`, `--nas-get-signal-info`
и другие. Все восемь упираются в таймаут: первые три успевают открыть устройство
и не получают ответа, дальше и открыть уже нельзя. `libqmi 1.38.0` и
`ModemManager 1.24.2` на аппарате стоят.

**Исправлен дедлок, из-за которого висла вся машина.** `mhi_ev_task()`
(`main.c`) берёт `mhi_event->lock` и уже под ним зовёт `process_event`. Мой
перенесённый `mhi_process_bw_scale_ev_ring()` брал тот же замок повторно —
рекурсия на спинлоке в тасклете, RCU stall, аппарат мёртв целиком (даже ICMP не
шёл). Штатные `mhi_process_ctrl_ev_ring` и `mhi_process_data_event_ring` замок не
трогают: его держит вызывающий. Сработало только на третий день, потому что
`mhi_irq_handler` ставит тасклет лишь на непустое кольцо, а запрос полосы модем
прислал впервые. Теперь разбор кольца идёт под замком вызывающего, а вызов
`bw_scale()` и ответ модему вынесены в `mhi_bw_scale_work()` на
`system_unbound_wq` — эта работа ничего не блокирует, поэтому дедлока 12.7 с
`mhi_ev_poll_work()` не даёт. Побочно подтвердилось, что механизм полосы вообще
работает: модем прислал `seq 1: speed 0x1 width 0x2` и получил ACK.

**Новые ручки модуля `mhi_pci_generic`:**

| ручка | назначение |
|---|---|
| `sdx_health=0` | `health_check` продолжает смотреть и печатать, но не запускает восстановление |
| `sdx_rpm=0` | запретить автоусыпление модема (2 с) |

`health_check` теперь печатает не голое «Device died», а что именно увидел:
слово vendor и код ошибки, `LNKSTA`, `MHICTRL`, `MHISTATUS`, EE и `pm_state`.

**Наблюдатели пишут в `/dev/kmsg`** (`mdmwatch.py`, `gpiowatch.py`, префиксы
`MDMWATCH:`/`GPIOWATCH:`) — иначе при зависании логи не долетают до диска.
`gpiowatch.py` после загрузки драйвера бесполезен: линии заняты `sdx-modem-ctrl`,
и `gpioget` возвращает «Device or resource busy». Состояние esoc надёжнее читать
из `cat /sys/module/mhi_pci_generic/parameters/sdx_reset`.

**Как снять лог зависания без TWRP.** Раздел 8 предлагает TWRP, но при живом Arch
проще: тёплый сброс (питание + громкость вниз, **не** долгое удержание питания),
загрузиться обратно и прочитать `/sys/fs/pstore/console-ramoops-0` штатным ядром.
Именно так найден дедлок. Перед опытом полезно `rm -f /sys/fs/pstore/*`.

**Что дальше.** Объявить каналы 10/11 (`EFS`) и написать хостовую службу,
отдающую модему `mdm1m9kefs1..3`. Протокол по этому каналу неизвестен; первый шаг
дешёвый — завести канал как порт WWAN (тем же приёмом, что и SAHARA в
`mhi_wwan_ctrl.c`) и посмотреть, что модем в него пишет. Даже без ответа станет
видно, открывает ли он канал и меняются ли те самые 16 с.

**Скрипты прогона:** `/root/run_amss.sh` (полный прогон: наблюдатели, Sahara,
`modprobe` с ручками, 120 с), `/root/qmiprobe.sh` (опрос QMI в окно жизни).
Логи — в `/root/logs/<штамп>/`, симлинк `/root/logs/last`.

### 12.12 Канал EFS: модем удержан в AMSS, IMEI и SIM на месте (01.09.2026, ночь)

**Стена в 16 секунд снесена.** Версия из 12.11 подтвердилась полностью.

Что сделано:

1. **Объявлены каналы MHI 10/11 (`EFS`)** в `mhi_qcom_sdx55_fusion_channels[]` и
   заведены портом WWAN через `mhi_wwan_ctrl.c` (тип `WWAN_PORT_XMMRPC` взят
   только ради имени узла — на этой плате он не занят, и порт не путается с
   firehose от SAHARA). Узел — `/dev/wwan0xmmrpc0`.
2. **Написан `/root/efs_srv.py`** — сервер удалённой файловой системы.

Первый же прогон показал, чего модему не хватало: через 9 мс после mission mode
он открывает канал и **сам первым шлёт Sahara HELLO** (48 байт, режим 2). На
`HELLO_RESP` отвечает `MEM_DEBUG` с таблицей регионов, а в таблице — регион с
именем **`m9kefs1`**, 2 МБ по адресу `0x80200000`. То есть канал служит для
синхронизации NV модема с флешем телефона.

После того как сервер стал вычитывать регионы и **закрывать сеанс командой
`RESET`**, поведение изменилось разом:

- `link DOWN` не случается вовсе, модем живёт часами;
- **`mdm2ap_status` встаёт в 1** — впервые за всю работу;
- на 124-й секунде приходит второй сеанс, уже `m9kefs2`, то есть модем работает
  штатно и периодически сбрасывает NV на хост.

**Заглушки EFS были фальшивкой.** Стоковые `efs1..3.bin` из `image/sdx55m`
подписаны внутри `IMGEFS- DUMMY-1`, занимают 512 байт и никакой NV не несут;
модем читал из них 40 байт заголовка и уходил в **factory-test без IMEI**.
Настоящие образы лежат в разделах `mdm1m9kefs1..3` (по 8 МБ, внутри по
2 096 680 значащих байт, заголовок `IMGEFS1T`, адрес загрузки `0x80200000`).
Сняты через `dd` в `/lib/firmware/qcom/sdx55m/efs{1,2,3}_real.bin`, и
`sahara_srv.py` теперь отдаёт слоты 16/17/20 из них. Модем выкачивает каждый
целиком.

**Что получилось после этого:**

| проверка | результат |
|---|---|
| `dms-get-revision` | `MPSS.HI.2.5.c1-00075-SDX55_RMTEFS_PACK-1.21664.4.33420.2` |
| `dms-get-ids` | **IMEI `869172056038182`** (было `unknown`) |
| `dms-get-operating-mode` | `offline` (было `factory-test`) |

(`uim-change-provisioning-session`) проходит для обоих слотов и ничего не меняет.
MCFG активны, так что дело не в конфигурации оператора.

**Живая SIM — в слоте 2**, ICCID `897011102602108870` (Yota). В слоте 1 карта,
скорее всего, мёртвая.

(модем отвечает `May 8 2024 ... sdx55.rm`), настройка масок F3 командой
`DIAG_EXT_MSG_CONFIG_F` (0x7D, операция 4, формат `<BBHI>` — всё, что шире,
отбивается как `BAD_PARM`/`BAD_LEN`).

**Грабли:** маска `0xFFFFFFFF` включает все уровни сообщений разом, и поток
кладёт модем — канал DIAG у нас с `MHI_WWAN_MAX_MTU = 0x400`, а читатель на
Python не успевает. Модем умер через ~15 минут работы именно после этого. По
умолчанию в скрипте теперь маска `0x18` — только `error` и `fatal`.
Правильное лечение — сделать MTU свойством канала, а не константой модуля.

### 12.13 Тракт данных и упор в `DeviceNotReady` (02.09.2026, ночь)

**Каналы данных заведены, и аппаратные кольца больше не убивают линк.** В 12.4
записано, что при `NHWER > 0` модем через ~100 мс ронял PCIe — это оказалось
следствием ранних неполадок, а не свойством платы. Добавлены
`MHI_CHANNEL_CONFIG_HW_UL/DL(100/101, "IP_HW0")` и два аппаратных кольца
событий, счётчик `link DOWN` остался нулевым. Появилось устройство
`mhi1_IP_HW0`, `modprobe mhi_net` поднимает `mhi_hwip0`, интерфейс встаёт в
`UP,LOWER_UP`. Каналы и кольца стоят **последними** в массивах, а ручка
`sdx_data=0` просто укорачивает счётчики и возвращает прежнюю конфигурацию.

Порты данных открываются и на уровне QMI:
`--dpm-open-port="hw-data-ep-type=pcie,hw-data-ep-iface-number=N,hw-data-rx-id=101,hw-data-tx-id=100"`
отвечает успехом для любого N из 1, 2, 4, 5. На `DeviceNotReady` это не влияет —
версия «CM ждёт тракт данных» не подтвердилась.

**Где именно упёрлись.** `dms-set-operating-mode=online` неизменно даёт
`QMI protocol error (52): DeviceNotReady`. При этом:

- `offline` ставится успешно, а `low-power`, `factory-test`,
  `persistent-low-power`, `mode-only-low-power` — все дают
  `InvalidTransition`. То есть переход в `online` модем считает **законным**, но
  не готовым: не готова какая-то его подсистема.
- Модем **каждую загрузку поднимается в `offline`**, причём это не заводской
  режим: NV 453 (`FTM mode`) прочитан через DIAG и равен 0.
- `dms-get-capabilities` возвращает пустой список сетей (`Networks: ''`) и
  нулевые скорости, `dms-get-band-capabilities` — `none`. При этом
  `nas-get-system-selection-preference` показывает **полный** набор:
  `gsm, umts, lte, 5gnr`, LTE 1–71, NR SA/NSA, выбор сети автоматический.
  То есть конфигурация есть, а радио не инициализировано.
- `nas-get-home-network` → `NotProvisioned`, хотя
  `uim-change-provisioning-session` проходит и `Primary GW` действительно
  переезжает между слотами. Приложение USIM в слоте 1 в состоянии `ready`,
  в слоте 2 (живая карта) — только `detected`; `uim-sim-power-on=2` отвечает
  `NoEffect`, то есть питание и так подано.
- `pdc-list-configs=platform` — ровно одна конфигурация,
  `SR_DSDS-SDX55_Fusion`, активна; `software` — 25 штук, активна
  `ROW_Commercial`. Конфигурации в порядке.
- Загрузочный журнал SBL перечисляет все двенадцать образов (TRDATA, APDP,
  QSEE Dev Config, QSEE, QHEE, AOP, EFS1..3, ACDB, Q6, APPS) без единой ошибки.
- Время модема верное, `dms-get-time` возвращает текущую дату.
- Возможность MHI TIMESYNC модем объявляет (id 2 по 0xa20), но, судя по времени,
  без неё он обходится.

**Что проверено и отброшено:** хостовое автоусыпление и health check (12.12),
тракт данных и DPM, конфигурации MCFG, заводской режим NV, мёртвая SIM в первом
слоте (на Android аппарат с ней работал), таймсинк.

**Следующий шаг — журнал F3 модема.** Он единственный скажет, какая подсистема не
готова. `/root/diagprobe.py` уже умеет разговаривать по `/dev/wwan0qcdm0`:
кадрирование HDLC, запрос версии, настройка масок (`DIAG_EXT_MSG_CONFIG_F`,
операция 4, формат `<BBHI>`) и **чтение NV-элементов**
(`python3 /root/diagprobe.py 0 0x18 nv 453,10` — команда `DIAG_NV_READ_F` 0x26,
пакет `cmd + item + 128 байт + status`). Маски принимаются, но F3-сообщений
модем в этот канал не шлёт ни при какой маске. На этой платформе журнал идёт
через **DCI** — стоковое дерево объявляет `mhi_chan@26/27 "DCI"`, а у нас этих
каналов нет. Их и надо завести следующим заходом.

**Важная особенность стенда:** EFS подаётся из неизменного снимка при каждой
загрузке, поэтому **любое изменение состояния модема теряется при перезагрузке**
— в том числе провизионирование и режим. Чтобы состояние жило, надо записывать
то, что модем отдаёт по каналу EFS (`/root/efs_writeback/m9kefs*`), обратно в
`efs{1,2,3}_real.bin` или прямо в разделы `mdm1m9kefs*`.

**Мелочь, стоившая времени:** короткое нажатие питания на этом аппарате
`systemd-logind` понимал как команду выключения, и телефон корректно гас посреди
опыта. Лечится `/etc/systemd/logind.conf.d/10-no-powerkey.conf` с
`HandlePowerKey=ignore` и `HandlePowerKeyLongPress=ignore`; аппаратный сброс
долгим удержанием при этом работает как работал.

**Службы QRTR на стороне хоста — проверены и не помогли.** Собраны и поставлены
на аппарат (`meson`/`make`, исходники в `/root/{qrtr,tqftpserv,pd-mapper}`):

- `andersson/qrtr` → `/usr/bin/qrtr-lookup`, `qrtr-cfg`. **`qrtr-lookup` очень
  полезен**: печатает все службы на шине с номерами узлов. Видно, что модем —
  узел 3 и что у него подняты NAS, UIM, WMS, Voice, PDC, DPM, Thermal, Time,
  IPA control и прочее, то есть его стек жив целиком.
- `linux-msm/tqftpserv` — модем **ни разу ничего не запросил**, лог пуст даже
  когда служба поднята до загрузки модема.
- `linux-msm/pd-mapper` — сам по себе говорит «no pd maps available», потому что
  ищет `.jsn` в каталоге прошивки устройств `remoteproc`, а модем на PCIe таким
  не является. Карты доменов лежат в разделе `modem_a`: `modemr.jsn` (рядом с
  образами SDX55) плюс `adspr.jsn`, `adspua.jsn`, `cdspr.jsn`. После копирования
  их в `/lib/firmware/qcom/sm8250/xiaomi/alioth/` служба поднимается и публикует
  «Service registry locator». На `DeviceNotReady` это не влияет — даже когда обе
  службы запущены **до** загрузки модема.

Обе добавлены в начало `/root/run_amss.sh` — вреда от них нет, а инструмент
`qrtr-lookup` стоит оставить.

### 12.14 Инструменты: чтение EFS модема по DIAG (02.09.2026, ночь)

Появился `/root/efsdiag.py` — **браузер файловой системы модема поверх DIAG**.
Это первая возможность заглянуть внутрь работающего модема, и она пригодится
для всего дальнейшего.

Транспорт тот же, что у `diagprobe.py` (HDLC, CRC-16/X-25 по
`/dev/wwan0qcdm0`), пакеты — `DIAG_SUBSYS_CMD_F` (0x4b) с подсистемой 0x13 (FS)
и кодом операции EFS2: `OPENDIR` 11, `READDIR` 12, `CLOSEDIR` 13, `OPEN` 2,
`READ` 4, `CLOSE` 3.

```bash
python3 /root/efsdiag.py /nv/item_files 1          # обход дерева, глубина 1
python3 /root/efsdiag.py "/policyman/policies.xml" cat
```

Тонкость, стоившая одного прогона: в ответе `READDIR` имя лежит **по смещению
36**, а не сразу за размером — между ними ещё три отметки времени
(`atime`, `mtime`, `ctime`).

`diagcomm_ctrl_send_mult_pkt - No pkt to write` из `diagcomm_ctrl.c`. Подсистемы
молчат: их маски идут не командой 0x7D, а через управляющий протокол DIAG,

### 12.16 Журнал F3 заработал; термодатчики усилителя читаются как −40 (02.09.2026)

Два приобретения: **читается собственный журнал модема** и найдена первая
физическая аномалия.

**Как удалось включить F3.** Раньше маски задавались наугад и молча не
применялись. Правильный порядок — по исходникам Xiaomi
(`drivers/char/diag/diagchar.h`, `diag_masks.h`):

| код операции `DIAG_EXT_MSG_CONFIG_F` (0x7D) | смысл |
|---|---|
| 1 | получить список диапазонов SSID |
| 2 | получить build-маску |
| **3** | **прочитать** маски сообщений |
| **4** | **записать** маски сообщений |
| 5 | записать все маски разом |

Я писал операцией 3 — то есть читал, и потому маски всегда возвращались нулями.
Правильная последовательность в `/root/diagprobe.py`:

1. операция 1 — модем отдаёт **25 диапазонов** SSID: `0..134`, `500..506`,
   `1000..1007`, `2000..2008`, `3000..3014`, `4000..4010`, `4500..4584`,
   `4600..4616`, `5000..5036`, `5500..5517`, `6000..6081`, `6500..6521`,
   `7000..7003`, `7100..7111`, `7200..7201`, `8000`, `8500..8532`,
   `9000..9008`, `9500..9521`, `10200..10210`, `10251..10255`, `10300`,
   `10350..10377`, `10400..10416`, `10500..10505`;
2. на каждый диапазон — операция 4 пакетом `struct diag_msg_build_mask_t`
   (`cmd, sub_cmd, ssid_first, ssid_last, status, padding`, ровно **8 байт**,
   дальше по 32-битной маске на каждый SSID диапазона);
3. затем `DIAG_EVENT_REPORT_F` (`0x60 0x01`) — без него поток всё равно молчит.

```bash
python3 /root/diagprobe.py 60 0xFF ranges      # маски всем диапазонам и слушать 60 с
python3 /root/diagprobe.py 0 0x18 nv 453,10    # чтение NV-элементов
```

После этого в журнал идут настоящие сообщения подсистем: таймеры `LTE_RRC_SIB`,
`tdsrrctmr`, замеры АЦП. Осторожно: маска `0xFFFFFFFF` при **неверном** формате
пакета один раз положила модем; с правильным форматом `0xFF` ведёт себя мирно.

**Найденная аномалия.** Модем регулярно снимает свои термодатчики, и картина
такая:

```
VADC conv result for XO_THERM:   nPhysical 35266   <- 35.2 °C, правдоподобно
VADC conv result for PA_THERM:   nPhysical -40
VADC conv result for PA_THERM1:  nPhysical -40
VADC conv result for SYS_THERM1: nPhysical -40
VADC conv result for SYS_THERM2: nPhysical -40
```

`-40` — нижний предел таблицы термистора, то есть «канал не читается».
Опорный генератор мерится нормально, значит АЦП работает, а вот датчики
усилителя мощности и корпуса — нет. Без достоверной температуры усилителя модем
не имеет права включать передатчик: это штатная защита. Версия не доказана, но
она первая, которая объясняет `DeviceNotReady` физически, а не догадкой.

Проверять дальше: где висят эти термисторы — на PMIC модема (`PMX55`) или на
PMIC процессора; и не должен ли хост передавать температуру модему через службу
`Thermal mitigation device` (QMI 24, экземпляр 100), которую модем публикует.

**Запись в EFS модема тоже работает** — `efsdiag.py <путь> write <hex>`,
операция `EFS2_WRITE` (5) с открытием в `O_RDWR`. Это безопасно: NV подаётся из
неизменного снимка при каждой загрузке, так что любая правка откатывается
перезагрузкой. Чтобы правка **пережила** перезагрузку, надо взять то, что модем
сам отдаёт по каналу EFS (`/root/efs_writeback/m9kefs1`), и подложить вместо
`efs1_real.bin`.

Замеченное при этом: `/nv/item_files/modem/mmode/high_capability_sub` = `0xff`,
то есть «подписка с высшим приоритетом не назначена», при `device_mode` = 1.
Запись нуля вживую ничего не изменила — элемент читается на старте модема.

**Перенесён цикл mission mode из стока.** `mhi_qcom.c` на событии
`MHI_CB_EE_MISSION_MODE` принудительно усыпляет устройство и тут же будит —
комментарий там прямо говорит «чтобы устройство переключилось на настройки PCIe
PHY боевого режима». В mainline этого нет. Реализовано как отдельная работа:
`mhi_pci_mission_mode_work()` ждёт 200 мс, уводит в M3, кладёт линк в D3hot,
поднимает и возвращает в M0. Обычный `mhi_pm_suspend()` для этого не годится —
он отвечает `-EBUSY`, потому что у каналов уже висят приёмные буферы; понадобился
`mhi_pm_suspend_force()` (добавлен в `pm.c` по образцу существующего
`mhi_pm_resume_force`). Цикл проходит успешно (`resume returned 0`), линк цел,
но радио так и не включается. Ручка `sdx_mm_cycle=0` отключает.

**Заведены каналы `TF` (22/23) и `DCI` (26/27)** с пассивным наблюдателем
`mhi_sdx_tap`, который печатает в dmesg всё, что придёт. Каналы открываются,
модем в них **не пишет ничего**.

**Ещё отброшено:** `pd-mapper` с картами доменов из раздела модема и
`tqftpserv` — модем к ним не обращается; переключение активного слота; запись
`high_capability_sub`; перебор режимов (`low-power`, `factory-test`,
`persistent-low-power` — все `InvalidTransition`, законен только `online`).

### 12.17 РАДИО ВКЛЮЧИЛОСЬ. Причина — TFTP по QRTR (02.09.2026, утро)

**Модем вышел в эфир и увидел сеть.**

```
qmicli -d qrtr://3 --dms-set-operating-mode=online
        [qrtr://3] Operating mode set successfully
        Mode: 'online'

qmicli -d qrtr://3 --nas-get-serving-system
        Radio interfaces: '1'  [0]: 'lte'
        Current PLMN: MCC '250'  MNC '2'        <- Россия, сеть МегаФона
        Registration state: 'registration-denied'

qmicli -d qrtr://3 --nas-get-signal-info
        LTE: RSSI -48 dBm, RSRP -77 dBm, RSRQ -12 dB, SNR 7.0 dB
```

**Чего не хватало.** Модем при запуске забирает у процессора файлы **по TFTP
поверх QRTR** — тот самый `tqftpserv`. Он у нас работал, но модем его не находил:

```
ERR :[tftp_socket_ipcr_modem.c, 220] could not resolve remote host
ERR :[tftp_protocol.c, 870] Timeout while WRQ
INF :[tftp_client.c, 1289] TFTP_STAT : /readonly/firmware/image/modem_pr/so/561_0_0.mbn
        ... адресат в логе: [sid = 4096, iid = 3]
```

Причина — **кодирование поля instance**. `libqrtr` упаковывает его как
`instance << 8 | version`, поэтому upstream-вызов `qrtr_publish(fd, 4096, 1, 0)`
даёт на проводе `0x0001`, а вариант «версия 1, экземпляр 3» — `0x0301`. Модем же
ищет службу с сырым значением **3**. Правильная публикация:

```c
/* tqftpserv.c: было qrtr_publish(fd, 4096, 1, 0) */
ret = qrtr_publish(fd, 4096, 3, 0);   /* version 3, instance 0 -> на проводе 3 */
```

Плюс модему надо отдать сами файлы. `tqftpserv` разрешает
`/readonly/firmware/image/...` относительно каталогов прошивки устройств
`remoteproc`, поэтому дерево из раздела модема кладётся туда:

```bash
mount -o ro /dev/disk/by-partlabel/modem_a /mnt/modem
cp -r /mnt/modem/image/modem_pr /lib/firmware/qcom/sm8250/xiaomi/alioth/   # ~40 МБ
mkdir -p /readwrite      # сюда модем пишет ota_firewall/ruleset, mcfg.tmp и прочее
```

После этого в логе `tqftpserv` видны нормальные обращения модема, ошибок
«could not resolve remote host» — **ноль**, и `online` проходит с первого раза.

**Как нашли.** Через собственный журнал модема (12.16). В простое он почти
ничего не пишет — сборка боевая, — но **на своём запуске выдаёт 1618 сообщений**,
и там всё сказано открытым текстом. Ловится так: `/root/diagboot.sh` ждёт
появления `/dev/wwan0qcdm0` и сразу задаёт маски всем 25 диапазонам SSID
операцией 4. Запускается из `run_amss.sh` до загрузки драйвера, лог — в
`/root/logs/<штамп>/diagboot.log`.

Мораль: не угадывать, а спросить у модема. На это ушло полдня перебора версий
(энергосбережение, тракт данных, DPM, MCFG, политики, калибровка, Thin UI,
таймсинк, цикл mission mode) — и ни одна из них не была причиной.

**Термодатчики оказались ни при чём.** `PA_THERM`, `PA_THERM1`,
`SYS_THERM1/2` по-прежнему читаются как −40, и это не мешает радио работать.
Версия из 12.16 не подтвердилась; строки оставлены как справка.

**Где стоим по регистрации.** Сеть модем видит и получает от неё внятный ответ,
но в неё не пускают:

- слот 1 — карта в состоянии **`illegal`**, сеть отвечает `registration-denied`;
- слот 2 (Yota, ICCID `897011102602108870`) — **не активирована**;
  `qmicli --uim-switch-slot=2` переключает физический слот успешно, но приложение
  USIM остаётся в `detected` и до `ready` не доходит, провизионирование не
  создаётся.

То есть упор теперь не в аппарат, а в саму SIM: её надо активировать, а для
активации нужен интернет с неё же.

**Полная последовательность запуска модема** (она в `/root/run_amss.sh`):

```bash
mkdir -p /readwrite
setsid nohup /usr/bin/tqftpserv &            # ОБЯЗАТЕЛЬНО, и с instance 3
setsid nohup /usr/bin/pd-mapper &            # не обязателен
modprobe qrtr_mhi
modprobe mhi_wwan_ctrl
setsid nohup python3 -u /root/sahara_srv.py &   # образы загрузки
setsid nohup python3 -u /root/efs_srv.py &      # NV модема
modprobe mhi_pci_generic sdx_health=0 sdx_rpm=0
# через ~20 с:
qmicli -d qrtr://3 --dms-set-operating-mode=online
qmicli -d qrtr://3 --nas-get-signal-info
```

### 12.18 Регистрация в сети и SMS — цель достигнута (02.09.2026, утро)

**Модем зарегистрирован в сети и отправил SMS.**

```
Registration state: 'registered'
CS: 'attached'    PS: 'attached'
Current PLMN: MCC '250' MNC '1' 'MTS RUS',  роуминг off
Radio interfaces: [0]: 'lte'
LTE: RSSI -59 dBm, RSRP -93 dBm, SNR 1.8 dB

```

**Что мешало карте инициализироваться — неверный AID.** Приложение USIM остаётся
в состоянии `detected` и провизионирование не создаётся, если
`--uim-change-provisioning-session` вызвать с чужим идентификатором приложения.
AID у каждой карты свой, его надо брать из `--uim-get-card-status`:

| карта | AID |
|---|---|
| МТС | `A0000000871002FF86FF0789FFFFFFFF` |
| та, что была в слоте 1 раньше | `A0000000871002FF49FF0589` |

```bash
qmicli -d qrtr://3 --uim-change-provisioning-session=\
"session-type=primary-gw-provisioning,activate=yes,slot=1,aid=<AID карты>"
```

Сразу после этого: `Application state: 'ready'`, `Primary GW: slot '1',
application '1'` и через несколько секунд `registered`.

Оговорка про libqmi 1.38: при неудаче эта команда печатает бессмысленное
«could not power off SIM» — на самом деле модем ответил `Internal`, а не про
питание. При верном AID печатает `Successfully changed provisioning session`.

**Отправка SMS — `/root/smssend.py`.** `qmicli` отправлять не умеет (его WMS
заканчивается на маршрутах), ModemManager этот модем не видит вовсе: ему нужен
сетевой интерфейс на шине QRTR, а наш на MHI. Поэтому разговариваем со службой
напрямую — QMI поверх QRTR это семибайтовый заголовок и TLV, отправленные на узел
и порт службы:

```bash
python3 /root/smssend.py "+79779335757" "текст латиницей"
        WMS at node 3 port 49
        result=0 error=0 SENT
        message reference: 16
```

Скрипт сам находит службу WMS через `qrtr-lookup`, собирает PDU SMS-SUBMIT
(полуоктеты номера, упаковка по семь бит GSM 03.38) и шлёт `WMS_RAW_SEND`
(`0x0020`) с TLV 1 формата `формат(1) + длина(2) + PDU`. Формат `0x06` —
GSM/WCDMA point-to-point. Первый байт PDU — нулевая длина адреса SMSC, то есть
«взять из SIM». Ответ разбирается по TLV 2 (`result`, `error`) и TLV 1 (номер
сообщения).

**Итог по модему.** Работает: загрузка, удержание в mission mode, NV, IMEI,
чтение SIM, весь набор служб QMI, тракт данных, включение радио, регистрация в
сети оператора и отправка SMS. Три вещи, которых не хватало и которые нигде не
описаны для mainline:

1. каналы MHI 10/11 (`EFS`) и сервер удалённой файловой системы (12.12);
2. настоящая NV из разделов `mdm1m9kefs1..3` вместо заглушек `IMGEFS- DUMMY-1`
   (12.12);
3. `tqftpserv`, опубликованный как `qrtr_publish(fd, 4096, 3, 0)`, и дерево
   `modem_pr` из раздела `modem_a` (12.17).

Не сделано: приём SMS (маршруты стоят в `transfer-only`, обработчика нет),
мобильные данные (нужен bearer через QMI WDS на `mhi_hwip0`), голос,
автозапуск при загрузке системы.

### 12.19 Приём SMS и мобильные данные (02.09.2026, утро)

**Приём SMS — `/root/smsrecv.py`.** Маршруты модема стоят в `transfer-only`:
входящие не хранятся, а отдаются зарегистрированному клиенту. Порядок:

1. `WMS_SET_EVENT_REPORT` (`0x0001`) с TLV `0x10` = 1 — подписка на входящие;
2. слушать сокет: уведомления QMI приходят на тот же порт, откуда ушёл запрос;
3. в TLV `0x11` лежит `ack_indicator(1) transaction_id(4) format(1) len(2) PDU`;
4. **обязательно ответить** `WMS_SEND_ACK` (`0x0037`) с этим `transaction_id`,
   иначе оператор считает сообщение недоставленным и повторяет его по кругу.

Тонкость разбора: в уведомлении QMI **нет адреса SMSC** в начале PDU — в отличие
от того, что отдал бы AT-модем. Разбор начинается сразу с типа PDU. Кириллица
приходит в UCS-2 (`DCS = 0x08`).

```
=== SMS from 79779335757 at 2026-09-02 09:06:28 ===
Проверка 3
```

Накопленное у оператора выдаётся при новой регистрации, так что после запуска
приёмника полезно дёрнуть `low-power` → `online`.

**Мобильные данные — `/root/data_up.py`.** Работают, 10 МБ скачались за 2.4 с
(≈4.3 МБ/с, около 34 Мбит/с), `curl` отдаёт HTTP 200, DNS оператора отвечает.

Три вещи, каждая из которых по отдельности всё ломала:

1. **Тип конечной точки — `embedded` (3), а не `pcie` (2).** С `pcie`
   `WDS_BIND_MUX_DATA_PORT` отвечает `Internal (3)` при любых номере интерфейса,
   мультиплексе и типе клиента — проверено перебором всех сочетаний.
2. **APN `internet.mts.ru` без логина и пароля.** С `mts`/`mts` вызов отбивается
   как `CallFailed (64)`, с APN `internet` — ошибка 14.
3. **QMAP и отдельный интерфейс `rmnet`.** При простом raw-IP сессия
   поднимается и получает адрес, но нисходящий поток до хоста не доходит:
   на `mhi_hwip0` TX растёт, RX остаётся нулём.

Ещё одна особенность: `qmicli` здесь не годится для запуска сессии. На QRTR
клиент QMI живёт в процессе, поэтому привязка порта в одном запуске и старт
сессии в другом дают `Unknown client 1 for service wds`. Оба шага должны идти по
одному сокету, и он же должен оставаться открытым, пока нужна сессия.

```bash
qmicli -d qrtr://3 --dpm-open-port="hw-data-ep-type=pcie,hw-data-ep-iface-number=4,\
hw-data-rx-id=101,hw-data-tx-id=100"
qmicli -d qrtr://3 --wda-set-data-format="link-layer-protocol=raw-ip,ul-protocol=qmap,\
dl-protocol=qmap,dl-datagram-max-size=31744,dl-max-datagrams=32,ep-type=embedded,\
ep-iface-number=4"
modprobe mhi_net rmnet
ip link set mhi_hwip0 up
ip link add rmnet0 link mhi_hwip0 type rmnet mux_id 1
ip link set rmnet0 up mtu 1500
python3 /root/data_up.py internet.mts.ru - - 4 1 3 &   # apn user pass iface mux ep_type
# из его вывода взять адрес и настроить интерфейс:
ip addr add <ip>/29 dev rmnet0
ip route add default dev rmnet0 metric 700
```

**Грабли, стоившая получаса:** `pkill -f smsrecv` **убивает собственный ssh-сеанс**,
потому что его командная строка содержит тот же образец — и трюк с
`[s]msrecv` не спасает, если в той же строке есть `smsrecv.py` или `smsrecv.log`.
Надёжно только разносить убийство и запуск по разным вызовам ssh и брать
якорный образец вида `pkill -f "^python3 -u /root/smsrecv"`.

### 12.20 ModemManager заработал: модем виден системе целиком (02.09.2026)

**Результат.** `mmcli -m 0` показывает модем как обычный:

```
state: registered   access tech: lte   signal quality: 73%
equipment id: 869172056038182       supported: gsm-umts, lte, 5gnr
device: qcom-soc    drivers: qrtr, mhi_net    plugin: qcom-soc
ports: mhi_hwip0 (net), qrtr3 (qmi)
primary sim: slot 1 (active), slot 2 тоже виден
imsi 250019254345932, iccid 89701018292543459325, operator 25001
```

Отправка SMS через него проверена: `mmcli -m 0 --messaging-create-sms=...` +
`mmcli -s 0 --send` → `successfully sent the SMS`. Это открывает весь
пользовательский стек — Phosh, Plasma Mobile, `chatty`, `gnome-calls`,
NetworkManager: все они ходят к модему только через ModemManager.

Понадобилось четыре вещи. Первые три — настройка, последняя — правка кода.

**1. Зависший `qmi-proxy`.** ModemManager открывает порт только через прокси, а
от прежнего запуска остался процесс, державший сокет; новый падал с
«Address already in use», а MM видел «Transaction timed out» и объявлял порт не
QMI-совместимым. Прямой `qmicli -d qrtr://3` при этом работал, что и сбивало с
толку. Проверка: `qmicli -p -d qrtr://3 --dms-get-operating-mode` — если через
прокси таймаут, а без него ответ есть, надо убить `qmi-proxy`.

**2. Правила udev** (`/etc/udev/rules.d/77-mm-sdx55-qrtr.rules`):

```
SUBSYSTEM=="net", KERNEL=="rmnet*",     ENV{ID_MM_PHYSDEV_UID}="qcom-soc"
SUBSYSTEM=="net", KERNEL=="mhi_hwip*",  ENV{ID_MM_PHYSDEV_UID}="qcom-soc"
SUBSYSTEM=="wwan", ENV{ID_MM_PORT_IGNORE}="1"
```

MM собирает модем из QRTR-узла (устройство `qcom-soc`), но требует, чтобы в том
же устройстве был сетевой порт, иначе отказывает с «Failed to find a net port in
the QMI modem». Наш `rmnet0` числится за PCI-устройством, потому что MM берёт
родителя от нижележащего `mhi_hwip0` — поэтому помечать нужно **оба**
интерфейса. Порты MHI прячем: `wwan0qmi0` на этом модеме не отвечает никогда
(управление живёт на QRTR), `wwan0xmmrpc0` занят нашим сервером EFS, и попытки
их опросить валят весь разбор по таймауту.

**3. Обе подписки должны быть провизионированы.** Иначе приложение второй карты
остаётся в `detected`, и картина слотов противоречива:

```bash
qmicli -d qrtr://3 --uim-change-provisioning-session=\
"session-type=secondary-gw-provisioning,activate=yes,slot=2,aid=<AID карты 2>"
```

**4. Правка ModemManager — выбор основного слота у двухсимочного модема.**
`mm_shared_qmi_load_sim_slots` в `src/mm-shared-qmi.c` перебирает физические
слоты и на каждом активном **перезаписывает** выбор:

```c
if (slot_status->physical_slot_status == QMI_UIM_SLOT_STATE_ACTIVE) {
    ctx->active_logical_id  = slot_status->logical_slot;
    ctx->active_slot_number = i + 1;
}
```

Логика исходит из того, что активен ровно один слот. У DSDS-модема активны оба,
поэтому побеждал последний — вторая карта. Дальше MM кешировал её ICCID как
основной, при включении перечитывал настоящую основную подписку и решал, что
карту подменили:

```
SIM identifier has changed: '897011102602108870F' -> '89701018292543459325'
```

и пересоздавал модем по кругу — в интерфейсе SIM появлялась и пропадала.
Исправление: не давать более поздним слотам перебивать меньший логический номер,
то есть основную подписку. Патч стоит предложить наверх — это общая проблема
любого DSDS-модема, а не наша особенность.

Собирается на аппарате: `meson setup build --prefix=/usr && ninja -C build`
(нужны `glib2-devel` и `bash-completion`), затем достаточно заменить один
двоичный файл `/usr/bin/ModemManager` — плагины остаются от пакета, версия та же.
Оригинал сохранён как `/usr/bin/ModemManager.pkg`. Исходники с правками — в
`/root/MM`.

**Замеченное попутно:** `mmcli` показывает `lock: sim-pin2` — это не мешает,
PIN2 нужен только для отдельных операций. И `model: 0` — модем действительно
отдаёт ноль, см. 12.13.

### 12.21 Почему в звонке нет звука (02.09.2026)

Сигнализация голоса работает полностью: набор, дозвон, ответ, разговор, отбой
(12.18), входящие тоже проходят. Звука нет, и вот почему.

Голосовое аудио у этой связки идёт **только по MHI**: в стоковом дереве есть
единственный узел `mhi_chan@80 "AUDIO_VOICE_0"`, и никаких линий I2S или TDM к
модему на плате нет. Канал заведён и у нас (`MHI_CHANNEL_CONFIG_UL(80, ...)`,
`DL_AUTOQUEUE(81, ...)`), пассивный наблюдатель `mhi_sdx_tap` на нём поднимается:

```
mhi_sdx_tap mhi1_AUDIO_VOICE_0: MHIDBG tap: listening
```

Но за целый разговор модем не прислал в него **ни одного байта**. Причина в
архитектуре: канал не предназначен процессору. В исходниках Xiaomi есть
`drivers/bus/mhi/devices/mhi_satellite.c` — механизм передачи канала MHI
**сопроцессору**. Голосовые кадры ходят напрямую между модемом и ADSP, а
процессор лишь проксирует настройку канала. Модем начинает поток только после
того, как на стороне ADSP создана голосовая сессия.

Создаёт её стек **q6voice** (MVM, CVS, CVP поверх APR), которого **в mainline
нет вообще** — ни одного из этих драйверов. Это не особенность нашего аппарата:
звук в звонке не работает на mainline ни на одном телефоне Qualcomm.

Чтобы завести, нужно: перенести `mhi_satellite` (передача канала 80 ADSP),
реализовать сессию q6voice поверх существующего APR и связать её с трактом ASoC.
Работа заметно крупнее всего, что сделано для данных, и это отдельный проект.

`/usr/local/bin/shell-switch phosh|plasma`: меняет `Session=` в
`/etc/sddm.conf.d/10-mobile.conf` и перезапускает греетер. Phosh поднимается и
отдельным юнитом `/etc/systemd/system/phosh.service` (тогда SDDM надо остановить,
а сессию Plasma добить `loginctl terminate-user phone` — иначе `phoc` не получает
DRM и падает с SIGABRT).

**Phosh из пакетов Arch не запускался**, и дело не в нём самом.

Симптом: оболочка стартует (`Phosh ready after 1.36s`) и тут же умирает с
`Error 71 (Protocol error)`. Трассировка (`WAYLAND_DEBUG=1` через drop-in для
пользовательского юнита `mobi.phosh.Shell.service`) называет причину:

```
zwlr_layer_surface_v1#80.set_size(0, 0)
zwlr_layer_surface_v1#80.set_anchor(14)        <- bottom|left|right, без top
wl_display#1.error(..., "height 0 requested without setting top and bottom anchors")
```

Phosh создаёт полосу «домой» **без высоты** (`phosh_home_new` в `src/home.c` не
передаёт её вовсе) и рассчитывает, что размер задаст расширение композитора
`zphoc_layer_shell_effects_v1` через *drag surface*. Но drag surface создаётся
только в обработчике `configure` (`src/drag-surface.c:208`), а до него дело не
доходит: композитор рвёт соединение на первом коммите.

**Апстримный `phoc` этого не допускает намеренно** — он собирается со **своей**
`wlroots`, в которую наложен патч
`subprojects/packagefiles/wlroots/0001-Revert-layer-shell-error-on-0-dimension-without-anch.patch`.
Тот оборачивает проверку высоты в `#if 0`. В Arch же `phoc` слинкован с
системной `wlroots0.20`, где проверка на месте.

Лечение: собрать `wlroots` с этим патчем и подменить библиотеку.

```bash
git clone --depth 1 -b v0.57.0 --recurse-submodules \
    https://gitlab.gnome.org/World/Phosh/phoc.git /root/phoc-src
cd /root/phoc-src/subprojects/wlroots-0.20.x
# патч из packagefiles контекстом не ложится на 0.20.2 - проверка
# desired_height == 0 оборачивается в #if 0 руками
meson setup b --prefix=/usr -Dexamples=false && ninja -C b
cp -n /usr/lib/libwlroots-0.20.so /usr/lib/libwlroots-0.20.so.pkg
cp b/libwlroots-0.20.so /usr/lib/libwlroots-0.20.so
```

Оговорки: `-Dembed-wlroots=enabled` и `--force-fallback-for=wlroots-0.20` при
сборке самого `phoc` **не помогают** — итоговый бинарь всё равно линкуется с
системной библиотекой; `diff_files` из wrap-файла молча не применяется.

**Заодно исправлено `libgmobile`.** В логе была жалоба `No panel found for
compatibles` и `gm_display_panel_get_name: assertion failed`: база устройств
(вкомпилированная, `data/devices/display-panels/*.json`) не знает `xiaomi,alioth`.
Добавлено описание нашего экрана — 1080×2400, 75×160 мм, скругления 60,
вырез под фронтальную камеру по центру сверху; файл зарегистрирован в
`data/gmobile.gresources.xml`, библиотека пересобрана (`-Dvapi=false`, иначе
требует `vapigen`). Это самостоятельный вклад: описание устройства стоит
предложить в gmobile, а патч `wlroots` — сообщить сопровождающим Arch, потому что
у них Phosh не работает ни на одном устройстве.

Оригиналы сохранены рядом: `/usr/lib/libwlroots-0.20.so.pkg`,
`/usr/lib/libgmobile.so.0.pkg`, `/usr/bin/phoc.pkg`, `/usr/bin/ModemManager.pkg`.

### 13.1 Итог по оболочкам и порядок запуска (02.09.2026)

**Выбрана Plasma Mobile.** Phosh запустился (после починки `wlroots`, см. 13) и
даже работал с мобильным интернетом, но внешне проиграл. Снесён:
`pacman -Rns phosh phoc phosh-mobile-settings squeekboard`, подменённые ради него
`libwlroots-0.20.so` и `libgmobile.so.0` возвращены из копий `.pkg`. Приложения
`gnome-calls` и `chatty` оставлены — они работают и под Plasma. Разбор причины
падения Phosh (13) сохранён: он не про наш аппарат, а про сборку Arch, и о нём
стоит сообщить сопровождающим.

**Порядок запуска перестроен.** Раньше `modem.service` сам держал сессию данных,
а `ModemManager` стартовал задолго до появления модема и не находил ничего.
Теперь разделение такое:

| кто | что делает |
|---|---|
| `modem.service` (oneshot, `RemainAfterExit`) | поднимает железо: `tqftpserv`, `pd-mapper`, модули, серверы Sahara и EFS, `modprobe mhi_pci_generic`, ждёт mission mode, включает радио, провизионирует **обе** SIM, готовит тракт данных (DPM, WDA, `rmnet0`), в конце **перезапускает ModemManager** |
| ModemManager | видит уже готовый модем |
| NetworkManager | владеет соединением: модем виден как `qrtr3 gsm` |

`/root/data_up.py` остался для подъёма данных руками, когда GUI не участвует, но
в автозапуске больше не используется: два владельца одной сессии только мешают
друг другу.

Проверено на чистой перезагрузке:

```
[08:22:09] registration: Registration state: 'registered'
[08:22:09] modem ready
mmcli -L        → Modem/0 [QUALCOMM INCORPORATED]
nmcli device    → qrtr3 gsm disconnected, wlp1s0 wifi connected
```

**Грабли этой части:**

- `ModemManager` **не был включён в автозапуск** — отсюда «модем то есть, то
  нет». Теперь `systemctl enable ModemManager`.
- В `awk` шаблон вида `Slot [1]:` **нельзя сравнивать регулярным выражением** —
  скобки читаются как класс символов, и совпадений не бывает никогда. Нужен
  `index($0, want)`. Из-за этого провизионирование молча пропускалось.
- После включения радио карте нужно несколько секунд, прежде чем она перечислит
  приложения; без ожидания AID не находится.
- Wi-Fi пропал не из-за rfkill (тот был чист), а из-за **внутреннего выключателя
  NetworkManager**: `nmcli radio wifi` показывал `disabled`. Его гасит переключатель
  в оболочке, и состояние переживает перезагрузку. Лечится `nmcli radio wifi on`.
- Выгружать `ath11k_pci` на ходу не стоит: устройство MHI остаётся в неполном
  состоянии, прошивка при повторной загрузке встаёт на середине. Помогает только
  перезагрузка.

### 13.2 Мобильные данные через ModemManager и NetworkManager (02.09.2026)

Модем полностью управляется из системы: `nmcli` показывает
`qrtr3 gsm connected Mts`, интерфейс `qmapmux0.0` получает адрес, пинг через
модем идёт без потерь. Плитка мобильных данных в оболочке работает.

Понадобилось **три правки ModemManager** (плюс та, что в 12.20). Все они —
следствие одного: MM написан либо под USB-модемы, либо под SoC с внутренним
модемом за IPA, а у нас внешний модем на PCIe.

**1. Плагин `qcom-soc` не знал наш тип интерфейса.**
`src/plugins/qcom-soc/mm-broadband-modem-qmi-qcom-soc.c`, `peek_port_qmi_for_data`
принимал только драйверы `ipa` и `bam-dmux`, отвечая на всё прочее
«Unsupported QMI kernel driver for 'net/mhi_hwip0': mhi_net». Добавлены
`mhi_net` и `rmnet`, они идут по тому же пути, что и IPA.

**2. Без мультиплексирования модем не работает вовсе.**
`src/mm-bearer-qmi.c`, `load_settings_from_bearer`: если пользователь режим не
задал, MM выбирает «без мультиплексирования» для всех драйверов, кроме `ipa`. А в
этом режиме он **никогда не привязывает клиента WDS**, и `Start Network`
отвечает `InvalidOperation (70)`. Для `mhi_net` теперь, как и для IPA, по
умолчанию `MULTIPLEX_SUPPORT_REQUIRED`. После этого MM сам создаёт `qmapmux0.0`
поверх `mhi_hwip0` и всё поднимается.

**3. Порядок и роли.** `modem.service` больше не держит сессию данных: она
принадлежит NetworkManager. Служба поднимает железо и в конце перезапускает
ModemManager.

**Ошибка, которую я повторил трижды, — нумерация типов конечной точки.** В libqmi
`QMI_DATA_ENDPOINT_TYPE_PCIE = 3`, а `EMBEDDED = 4`. В ручных пробах
(`bindprobe.py`, `data_up.py`) параметр «3» назывался «embedded», хотя это
**pcie**. Отсюда родились две неверные правки: сначала в `modem-up.sh` формат
данных задавался с `ep-type=embedded` и отбивался, потом в MM менялось
сопоставление `mhi_net → EMBEDDED`, что ломало согласование формата. Правильно
так, и обе стороны используют **один и тот же** тип:

| шаг | тип конечной точки | номер интерфейса |
|---|---|---|
| `WDA Set Data Format` | `pcie` (3) | 4 |
| `WDS Bind Mux Data Port` | `pcie` (3) | 4 |

То есть собственный выбор MM был верен с самого начала; мешало только отсутствие
мультиплексирования.

**Прочее из этой части:**

- Заранее созданный вручную `rmnet0` мешает MM: он отвечает
  «Cannot switch to non-multiplex setup: 1 links already setup exist». Свои
  ссылки надо удалять, MM создаёт их сам.
- APN `internet.mts.ru` **без логина и пароля**; с `mts`/`mts` вызов отбивается.
- В профиле NetworkManager полезно отключить IPv6 (`ipv6.method disabled`) —
  модем его не даёт, и MM тратит на это попытку.

Патчи ModemManager лежат в `/root/MM` (ветка `1.24.2` с правками), собранный
двоичный файл — `/usr/bin/ModemManager`, оригинал пакета сохранён как
`/usr/bin/ModemManager.pkg`, плагин — `libmm-plugin-qcom-soc.so.pkg`.
Все три правки общего характера и годятся для upstream.

### 13.3 Wi-Fi: MAC-адрес и пропадающая сеть

**Телефон каждую загрузку получал новый MAC** (`00:03:7f:12:xx:xx`, префикс
Atheros): `ath11k` не находит настоящий адрес в данных платы и генерирует его.
Роутер видел нового клиента каждый раз, привязать по MAC было невозможно.

Настоящий адрес лежит в разделе `persist`, файл `wlan_mac.bin`
(`wlan0=8c7a3dc0df17`). Сделано:

- `/usr/local/bin/wlan-mac.sh` + `wlan-mac.service` — читает адрес из раздела и
  выставляет на интерфейс до запуска NetworkManager;
- `/etc/NetworkManager/conf.d/00-mac.conf` — `wifi.scan-rand-mac-address=no` и
  `wifi.cloned-mac-address=8C:7A:3D:C0:DF:17`.

Тонкость: одной установки адреса через `ip link` мало — NetworkManager
возвращает «постоянный» адрес, а постоянным он считает как раз выдуманный
драйвером. Помогает только явный `cloned-mac-address`.

**Wi-Fi пропадал** не из-за rfkill (тот был чист), а из-за внутреннего
выключателя NetworkManager: `nmcli radio wifi` показывал `disabled`. Его гасит
переключатель в оболочке, и состояние переживает перезагрузку. Лечится
`nmcli radio wifi on`.
